# 体积云

云覆盖度立方图（`Domain::CubeMap`，六面沿行堆叠）+ 云壳内的体积 raymarch，以及云密度场的正确梯度组装。

## §39 云覆盖度图 + 体积云（阶段 1–2）

**形状**：云直接用一张 cubemap，高度上的分布和细节用 shader 提供 ✓。理由：64³ 体积铺满 `[-1.1,1.1]³` 时体素边长 0.0344，而云带只有 0.05 厚 ⇒ **竖着只有 1.45 个体素** ✗，PCG 表达不了云顶/云底。
高度交给 shader 之后，**烘出来那张图不需要垂直分辨率** ✓ ⇒ 既不用 `Volume3D`、也不用 `texture_cube_array`，连 §24.4 预判的"把算子泛化到 3D"都免了 ✓。
地面云影走**自写 surface material**（"自写，反正也要换 cubemap"）✓ —— 落在阶段 3/4。

### §39.2 `Domain::CubeMap`：六面沿行堆叠

- **布局**：`width = 面边长`、`height = 6 × 面边长`，行主序 ⇒ **与 wgpu 的 cube 层布局逐字节一致** ✓，上传时不用重排 ✓（`clouds::coverage_image` 只做 f32 → f16）。
- **面朝向：代价 0** ✓。仓里原有的 `cube_direction` / `cube_face_of` **本来就已经是** wgpu 的约定（面序 +X −X +Y −Y +Z −Z，面内朝向也一致）✓ —— §35 代价表里"面朝向：小但真实"那一格实际没花钱 ✓。
- **验证方式（值得照抄）**：把覆盖度**直接当颜色输出**（`return vec4(vec3(mask), 1.0);`），热重载看一眼：整球图案连续、六面缝合处无痕 ⇒ 约定端到端正确 ✓。总览图看不出这个，**这个判据是唯一能证明它的** ✓。
- `px_ops` 侧 `sample_direction` 走**跨面双线性** ✓（面的四条边是别人的纹素，通用 uv 路径会 clamp）。两条连续性测试让一张光滑解析场跨 +X/+Z 与 +X/+Y 棱走一遍：正确实现最大跳变 < 0.02，clamp 实现是 **0.43** ✗。

### §39.3 四条必须遵守的规则

1. **凡声明 `#define_import_path` 的 WGSL 模块都必须被当作资产加载** ✓。否则每个 import 它的管线都报 `Shader import not yet available`，而 Bevy 会一直重试（`pipeline_cache.rs:688` 把它重新入队）
   ⇒ 永久失败且**不报错到日志** ✗。现由 `ShaderLibraryPlugin` 扫 asset 目录、凡声明 import path 的一律加载
   （`atmosphere.rs` 里那个"写了没人读"的 `ShaderLibrary` 就是在干这件事，只服务 `common.wgsl` 一个库）。
2. **就绪判据不能把"失败"当"完成"** ✓：管线编译失败时必须判不就绪，并把**管线名 + 错误原文**打出来。否则会出一张**少了那个材质的"成功"图** ✗。**症状特征**：一整轮参数扫描的 PNG **字节数完全相同** ✗（极易被误读成"云太薄"）。
3. **`--serve` 必须有"空闲"这个状态** ✓：没活时把相机 `is_active` 关掉，有活了再打开、照样留 6 帧预热。
   否则离屏相机空闲也全速画，体积云把 GPU 持续占住 ⇒ 空闲的服务器在 **20–120 s 内必然掉设备** ✗（DX12 `DXGI_ERROR_DEVICE_REMOVED` = `0x887A0005`，日志里先看到的是下游症状：
   `Command allocator creation failed`、`clustering metadata staging buffer is invalid`）。
   A/B：同一台服务、同一颗行星、**只去掉云**，空闲 120 s **零掉设备** ✓；带云的每次必掉 ✗。
   修完实测：**空闲 240 s ✓ ＋ 连打 30 张图全成 ✓，零掉设备** ✓，且出图**逐字节不变** ✓。
   ⚠ "连续热重载之后每张图涨到 5–7 s"**不是热重载的锅** ✗ —— 那是同一个劣化过程的前兆（先变慢、后掉设备）；"改 shader ⇒ 不重建不重启"本身没错 ✓。
4. **怀疑"shader 被内联成一坨巨大字节码"⇒ 能量的就别猜** ✓：`tests/shaders.rs` 把每个入口 shader 过一遍 **naga 的 HLSL 后端并报体量**（涨一个数量级就失败）✓。实测 `clouds.wgsl` → **503 行 HLSL**（对照 `atmosphere.wgsl` 182 行）✓；naga 把 `gradient_noise_3` 输出成**真函数 + 真循环** ✓，两个 march 循环的边界是 uniform ⇒ **驱动也展不开** ✓。
   ⇒ WGSL 的内联确实是按调用点复制的 ✓，所以"循环体里塞几个噪声函数"值得量 ✗ —— 只是这次量出来没那么大 ✓。

## §43 云密度场的**正确**梯度组装

**完整且经验证的形式**（用 shader 里的名字，`along = across·span()`，所以 `along/span = across`）：

```
P_t = I − d⊗dᵀ                                    // 切向投影算子

∇_p ρ = (ρ_a / span) · d                                              // ① 高度
      + ρ_n · [ (s/r)·P_t·g_q  +  (along/span)·(d·g_q)·d ]            // ② 噪声
      + (ρ_cover / r) · P_t · g_cover                                 // ③ 覆盖度贴图
```

被淘汰的形式 ✗ —— 只有在"∂ρ/∂r 是固定 d 的真偏导、且 ∇_d ρ 已经是切向"时才对：

```
∇ρ = (∂ρ/∂r)·r̂ + (1/r)·∇_d ρ
```

⚠ **②中方括号里第二项是最容易漏的，而且漏了是灾难性的** —— 因为 `q` 通过 `a` 依赖 `r`，**噪声有一个"超出 ∂ρ/∂a"的径向依赖**。实测（20000 个壳内随机点，对比三维中心差分）：

| 组装方式 | 中位数 | 最大 |
|---|---|---|
| **正确** | 1.3e-07 | 2.0e-05 ✓ |
| 漏掉 `P_t` 投影 | 3.0e-01 | 6.2 ✗ 百分比级错 |
| **漏掉 `(along/span)(d·g_q)d`** | **7.0e+00** | **9.7e+01 ✗✗ 灾难** |
| 往 `g_cover` 里加 3.7·d 的径向垃圾 | 与正确**逐位相同** ✓ | ← `P_t` 把它吃掉了 |

⇒ **③ 只需要 `g_cover` 的切向部分** ✓ —— 所以**那张烘焙图正好就是答案**：一次 `textureSampleLevel` 同时拿到 mask 和梯度，再 `P_t` 投影 ✓✓。用户那句"梯度不是烘焙了吗，只需要一次采样"**完全成立** ✓。

⚠ 但必须确认 `gba` 是**喂给 `coverage_of` 的那个标量**的梯度（`.r` 的 mask）。现在 R=`mixed`、GBA=`∇mixed` ✓ 一致；但 `coverage_of` 之上还套了 `smoothstep(0,0.45, clamp(...))`，所以 `∂cover/∂mask = 6t(1-t)/0.45 · 1/max(1-coverage,1e-4) · [0<t<1]` ✓。

### §43.1 分段点的处理约定（不是障碍，是约定）

`smoothstep` 的导数在两端**自己归零**（实测 `s'(0)=0`、`s'(1)=0`），所以 CAS 输出里那堆 Piecewise/Heaviside **会塌缩成一串 `select(...)`** ✓ —— 12 行就能转写完：

```wgsl
let t1 = clamp(a / base, 0.0, 1.0);
let ds1 = select(0.0, 6.0 * t1 * (1.0 - t1) / base, t1 > 0.0 && t1 < 1.0);
let dc_dn = select(0.0, top * detail_strength, m > base + 0.02);
```

⚠ 需要显式决定的：**解析梯度要不要在"值被强制为 0"的地方也返回 0** ✓ —— 现在两条路径都在 `altitude` 出壳或 `cover <= 0` 时直接返回 0 ✓，与 FD 版一致 ✓。⚠ **找面不靠梯度** ✓：找面靠的是对 `cloud_field` 的步进（`if cloud_field(point) > SURFACE_LEVEL { break }`），**梯度只用来算法线** ✓ ⇒ 换解析版不改变找面的行为；硬表面云**已经换掉了** ✓。

### §43.2 工具选型（已调研，不要再重新查）

| 工具 | 结论 |
|---|---|
| **`num-dual`**（MIT OR Apache，活跃） | ✓ **用它**。但**不做 `px_ops` 的 dev-dependency，也不是那个 crate** —— 见 §45：它住在一个**独立 crate `px_verify`** 里 ✓（用户否掉了塞进 `px_ops`：脚手架不该长在出图的 crate 上）。`default-features = false` 可以甩掉 `nalgebra`/`simba` ✓ |
| `symbolica` | ✗ **不要**。源码可见但**非开源**：受雇使用需付费 **EUR 3000/年/开发机**，CI 单独报价 |

### §51.7 结论一：上界早退可证明不变，实测 **−38%**

**它是什么**：在 `cloud_field` 的最后一句之前插入（`bound` 是 clouds part 的参数，不是第二份 shader）：

```wgsl
if params.bound != 0u && shape_of(cover, medium.altitude, 1.0) <= params.surface_level {
    return 0.0;
}
```

⚠ 已被 §51.12 作废（−38% 的绝对值虚、方向未知）；修后重测见 §51.13。原文保留。

**为什么逐字节不变**：`shape_of` 对 `noise` 单调非降，`billows` 被 clamp 在 `[0,1]` ⇒ `shape_of(cover, altitude, 1.0)` 是精确上界；硬表面步进只问 `> surface_level`，上界都够不着 ⇒ 那里永远打不中。体积那条路根本不读 `cloud_field`，所以一个像素都不受影响。

**判据（实测）**：`orbit-surface.toml` 与 `orbit-bound.toml` 的 `params` 行**逐字相同，唯一功能差异是 `bound = 1`**。

| 分辨率 | `orbit-surface` | `orbit-bound` | 逐像素差 |
|---|---|---|---|
| 2240×1400 | `1CB44BF4EA90563A…`（1622592 字节） | 同一哈希 | **0 / 12544000 通道** |
| 480×300 | `AFCCB6402EC67631…`（124433 字节） | 同一哈希 | 0 |

（2240 那一档复现 4 次：冷启动+热身后批量 1 次、同服务连续批量 3 次。）

**帧时间（2240×1400，单档冷启动各一次，n=8，窗口期利用率都 100%）**：

| 场景 | min | 中位 |
|---|---|---|
| orbit-bare（无云） | 14.56 | 14.69 ms（**利用率仅 24–78%** ⇒ 这是地板） |
| orbit（体积云 56 步） | 21.82 | 25.70 ms |
| orbit-surface（硬表面 56 步） | 25.42 | **30.00 ms** |

⇒ **中位 30.00 → 18.56 ms（−38%），min 25.42 → 17.84（−30%）**，而且它是唯一能在 2240×1400 上单独跑完 8 个窗口的硬表面档。

**仪器天花板（如实记）**：

- `2240×1400` + `--fps`（不限帧）连续提交几千帧之后，**`orbit-surface` 会把驱动打挂**（`DEVICE_REMOVED` / `0x887A0005`），所以"四档 × 3 轮交错"的原始表格拿不到，上面只能给单档冷启动 n=8。现在这条失败是**大声**的（harness 的 fail 模式含 `设备实例已经暂停|0x887A0005`），不再伪装成 240 s 超时。

- ⚠ **冷启动后第一个请求仍可能丢云壳**（装 shader 打回重编的窗口，§52.3）：`p13-surface.png`（1312701 / `E1F99E4B…`）就是这一张。⇒ **仪器必须先热身一张再取判据**（handoff P14）。

### §51.8 工具层的坑（顺手记）

`tools/frame-probe.ps1` 原来把场景参数写成 `param([string[]]$Args)` —— PowerShell 的自动变量 `$args` **不分大小写**，于是参数被悄悄顶掉、请求退化成"经济世界"那条路。与更早那次 `$height` 顶掉 `[int]$Height` 是同一类。**参数名别和自动变量撞**：`$args` / `$input` / `$pid` / `$error` / `$host`。
（写文档时又踩了一次同胞：**编辑/读取工具的相对路径按会话工作区解析，不按 shell 的 workdir** —— 用 worktree 工作时一律给绝对路径。）

### §51.9 结论二：**梯度不是大头，步进是**

**前提核对（§43 成立）**：硬表面分支里 `cloud_field_gradient_analytic` 只有**一处**调用，位于步进循环**之后**、`found` 之后，只用来算法线 ⇒ 换成常量法线后**步进次数与命中位置一字不变**，两档之差才是"梯度那一步"的代价。

⚠ 已被 §51.12 作废（同上：泄漏期 DX12）；修后重测见 §51.13。原文保留。

两条独立佐证：

- 像素侧：`surface↔allmiss` 与 `nograd↔allmiss` 的"不同像素数"**完全相同（420513 / 3136000 = 13.41%）** ⇒ 哪些像素有云在两档里一模一样（**梯度只决定明暗，不决定找面**）。
- `orbit-allmiss`（`surface_level = 10.0`）的图与"干脆没有 clouds part"的 2240×1400 图**逐字节相同**（1312701 字节 / `E1F99E4B…`）⇒ 全 miss 时云壳贡献**恰好零个像素**，消融是干净的。

**四档（1920×1200，四档同一分辨率，单档冷启动 n=8）**：

| 档 | min | 中位 | 窗口期利用率 |
|---|---|---|---|
| orbit-bare（无云） | 14.61 | 15.72 ms | **25%**（地板） |
| orbit-surface（硬表面 56 步） | 20.26 | 26.80 ms | 100% |
| orbit-nograd（梯度换常量） | 19.95 | 25.52 ms | 100% |
| orbit-allmiss（`surface_level = 10`） | 22.44 | 29.43 ms | 100% |

**三条算式**：

| 问什么 | 算式 | 结果 |
|---|---|---|
| 解析梯度值多少 | `surface − nograd` | min **+0.31** / 中位 **+1.28 ms**（三次配对中位全正：+1.06…+1.99；min 落在 ±0.55 ms 的重复抖动里） ⇒ **≈1–2 ms，min 量不出来** |
| 命中的早退省下多少 | `allmiss − nograd` | min **+2.49** / 中位 **+3.91 ms**（为正 ⇒ 全 miss 比"能命中就早退"贵） |
| 全 miss 的步进代价 | `allmiss − bare` | min **+7.83** / 中位 **+13.71 ms** |

⇒ **成本大头是"走步"，不是"算法线"**。这与 §51.7 互相印证：上界早退砍掉的正是全 miss 那条路上的步进（−38%），而梯度只值 1–2 ms。所以优化该往"**少走步**"做（上界早退 / 粗到细 / Lipschitz 自适应），不该往"优化梯度"做 —— 后者即便做到免费也只值 1–2 ms。

⚠ **仪器天花板（第二次撞到）**：2240×1400 上 `orbit-nograd` 与 `orbit-allmiss` 的第 2 遍都被驱动移除（`0x887A0005`，fail-fast 报出）。所以三条算式改用 **1920×1200**（四档齐全；**分辨率是换过的，这里明写**），2240 只有 surface / nograd 各 1–2 遍，其配对差同样是"1 ms 量级、贴着噪声"。
⚠ `bound` / `gradient` 都用 `optional_number(...)? as u32` 读 ⇒ `gradient = 0.5` 会被**静默截断成 0**（handoff P16）。
⚠ 冷启动**第一个请求**仍会偶尔丢云壳（§52.3 同一个坑）⇒ 取判据前先热身一张（P17）。

### §51.10 下一步：外接代理 mesh，砍掉"射线穿过空壳"的那部分

**为什么是这个**：§51.9 说大头是**步进**（全 miss 7.8–13.7 ms），而其中真正被浪费的是**射线穿过空壳却没命中**的那一段。外观不用改就能砍掉的正是这一部分。

**形状**：在 PCG/CPU 烘一张**外接代理网格** —— 对 `cloud_field` 求等值面（marching cubes / surface nets 那类），并**整体向外膨胀若干格距**以保证**包住**真实等值面。它**不参与着色**，只用来收窄 raymarching：

- 最省的形式：让云的 fragment shader **就跑在这张代理网格上**（今天的云壳是 `ico(64)` 球壳，未命中的像素要沿射线走满 56 步；换成贴合的代理后，空区域的像素在**光栅阶段就被剔除**，剩下的也从离真实表面更近的地方起步）。
- 更保守的形式：代理渲进深度缓冲，云的步进只走 `[entry, exit]` 区间。

**判据：逐字节相同**（与 §51.7 同一条）。代理保守 ⇒ 不该丢任何命中。
⚠ 但代理的**镶嵌与轮廓**会改变 fragment 集合 ⇒ 若逐字节不同，必须能证明差异只落在"本来就不命中"的像素上；否则就是**轮廓处漏了**（外扩量不够），那是硬失败，不是"差一点"。

**架构（用户定，别改）**：这种重型算子的**协议定义在 `px_ops`**（可序列化的参数 + 数据交换的 Rust interface），**`pcg` 与"算子的真实实现库"都依赖这份协议** —— 于是换库不动 pcg，重算子也进不了 bevy 那一侧。实现 crate 是**叶子**（只依赖接口），由 `px_graphs` 把两边接上。

**还没定**：

- 库选型（调研中：Rust crate 或 binding；输入模型/许可证/维护状况/能否指定活跃单元）。
- **网格参数化**：壳很薄、角向全向 ⇒ 世界空间包围盒上铺均匀网格会浪费约 90% 采样；倾向立方图对齐的 6 面 × N² × 深度，或自己做稀疏分块。
- 外扩量怎么定（按格距的函数；膨胀必须单调，否则轮廓会出现缝）。

调研给出三个候选（`isosurface` / `isomesh` / `imlet`，都吃**回调**、都不需要稠密数组），但留了两个未知：**alpha 版能不能在现代 stable 上编过**、**没有任何吞吐实测**。两件都自己跑掉了（`target/isosurface-probe/`，30 行，只依赖 `isosurface = "=0.1.0-alpha.0"`，零传递依赖）：

| depth | 顶点 | 采样 | 稠密需要 | 省 | 耗时 |
|---|---|---|---|---|---|
| 4 | 480 | 1,361 | 4,913 | 4× | 1.2 ms |
| 6 | 7,824 | 25,297 | 274,625 | 11× | 23.7 ms |
| **7** | **31,608** | **100,433** | 2,146,689 | **21×** | **134 ms** |
| 8 | 126,480 | 392,913 | 16,974,593 | 43× | 721 ms |
| 9 | 506,064 | 1,560,913 | 135,005,697 | **86×** | 3,792 ms |

（单位球 r=0.32、等值面 0、域 `[0,1]³`、`LinearHashedMarchingCubes` + `IndexedVertices`，release，采样次数是回调里计数的。）

- ✅ **编得过、跑得起**：alpha 版在当代 stable 上零依赖编过（风险清单里的第 2 条解除）。
- ✅ **剪枝是真的**，而且比调研的估算好：depth 9 省 **86×**（估算说的是 18×）。
  ⚠⚠ **但自适应那条路最后没用**（实测否掉，见 §51.10.3）：`LinearHashedMarchingCubes` 的顶点位置依赖 HashMap 遍历序（同进程跑两次，depth 7 有 1251/14721 个顶点位置不同 ⇒ **内容寻址缓存直接失效**），而且它在域壁上把交点放在离壁半格处 ⇒ 相邻两面的切割折线错开一格、焊不严（实测 887 条开口边 / 950 条非流形边）。换成同 crate 的**稠密 `MarchingCubes`、逐面烘再按位置焊** 才闭合且可复现。所以"省 86×"这个好处我们**没拿到**，拿到的替代好处是"面很小"（6 面各 33³）。
- **代理要粗**：库自身约 **0.4–1.2 M 采样/秒**（回调是 trivial 球面 ⇒ 这几乎全是库 + 顶点去重的开销），比我们的场（约 200 ns/次）还贵约 5 倍。**外接代理只要 3 万顶点量级** ⇒ depth 7 = **134 ms**，加我们的场约 +20 ms ⇒ **一次烘 ≈ 150 ms**，且产物进缓存。
- ⚠ **这张表是距离场的数**（球面 `|∇f| = 1`）。我们的 `cloud_field − 0.20` 不是距离场，**必须先按梯度上界 `L` 归一化**，否则八叉树会剪掉含真表面的节点、代理出洞（失败方向是"缺失"）。⇒ `L` 是本方案正确性的枢纽，而任何文档都没写它怎么取 —— 必须自己测（§43 的解析梯度 + §46.3 的仲裁者就是量它的机器）。
- ⚠ 提取器在高分辨率下开销占主导（顶点去重的哈希）⇒ 别拿它出渲染网格，那是另一件事。

#### §51.10.2 保守性是**结构给的**，不是量出来的

细节场在 shader 里是**乘上去**的、而且 `detail ∈ [0,1]`：

```
final(p) = coarse(p) · detail(p)  ≤  coarse(p)
{p : final(p) > τ} ⊆ {p : coarse(p) > τ}
```

⇒ **粗场的等值面天然包住最终等值面**。代理的保守性是**结构性的**：不需要经验外扩量，也不需要为"包住"去测 Lipschitz 界。

三条推论：

- 代理 mesh 就烘 **`coarse = shape_of(cover, altitude, 1.0)`** —— 这正是 §51.7 那个**上界**，也就是早退优化用的同一个量（一个量、两处用）。
- 余量只需为**网格的线性逼近误差**留（弦误差 ≤ 一个单元对角线），不必为"包住"留。
- **粗场比全场便宜**：它不含 5 个八度的 `billows` ⇒ 烘代理时每次采样远低于 200 ns ⇒ §51.10.1 那张表里的场开销还要往下调。

⚠ 但 **`L` 仍然要测**：`isosurface` 的八叉树剪枝测试（`|f| < size·√3`）只在近似距离场时**不漏**。它决定"**网格有没有洞**"，与"包不包住"是两件事 —— 有洞 = 代理不闭合 = 硬失败。所以 `L` 归一化照做（§51.10.1 那条警告仍然成立）。

⚠ 判据因此可以更强：既然包住是**可证明**的，`orbit-surface` 与"跑在代理 mesh 上"的两张图应当**逐字节相同**；出现差异就说明代理漏了（不是"差一点"）。

#### §51.10.3 烘焙侧已交付（实测）

⚠ 部分被 §51.10.4 撤销：「必须包住」不再被要求（用户裁决）；烘焙交付与其数字保留。原文保留。

**两处偏离（都拿实测顶回来的）**：

- **不用自适应提取器**（见 §51.10.1 的更正）：几何不可复现 + 域壁半格偏移 ⇒ 焊不严。改用同 crate 的稠密 `MarchingCubes`，**逐面烘 + 按位置焊**（1e-4 容差 + 查 27 个相邻量子格，因为接缝方向只到浮点级相同，出现过 `−0.0` vs `0.0`）。
- **仍要一次保守化：切向邻域最大值（`reach=1`，至多外扩一格）**。§51.10.2 那条"保守性是结构给的"只覆盖"细节场乘法"（`final ≤ coarse`），**没覆盖点采样本身的欠采样**：覆盖度细节波长只有约 2.7 格 ⇒ 65² 网格上峰值能被低估一半，实测 **2/212 条方向上粗场超阈、网格却整块缺失**。取邻域最大值 = 把场换成它自己的膨胀 ⇒ 等值面是"真等值面的膨胀"，**方向是安全的那一边**。⚠ 径向最大值**不能碰壳的上下两层**（壁上场是 0/负，一动就变正、等值面切在域壁上：实测 3027 条开口边）。

**`L`（梯度上界，参数空间里）**：稀疏网格量到 **≤140.67**，稠密（6×256²×96）**≤227.94** ⇒ 参数写 `scale = 240.0`（留 5% 余量，每次烘完断言"量到的 ≤ scale"）。
⚠ 诚实标注：这是**测出来的下界**（连续统上的真 sup 可能略高）；而且当前的稠密 MC **与尺度无关 ⇒ L 取多少都不会造成洞**，它留在协议里是为了以后要接自适应提取器（剪枝测试只在 `|∇f| ≤ 1` 时不漏）。

**还没做**：接 shader（下一步）；自交统计；`node()/mesh_node()/volume_node()/surface_node()` 四者有复制粘贴（没重构，怕动到既有产物的键）。

#### §51.10.4 「包住」这个要求被撤销了（用户裁决）

**撤销**：代理 mesh **不需要包住**。理由：fragment 落点上的场值若已经 > 阈值，就朝相机那侧（往回）步进找入射面；不够就照常往前。于是 mesh 在内、在外、切穿云都行。

卸掉的：

- **径向要求整个消失** ⇒ §51.10.3 里 depth 5 那个 −0.000149 的"没严格包住"**不再是缺陷**（depth 6 也就没必要了）。
- 不需要为包住做任何外扩；`L` 对"包住"不再必要（只留给自适应提取器的剪枝不漏）。
- 失败模式从"**整块云消失**"退化成"**多走几步**"。

**没卸掉的（别混淆）**：

- **几何缺失仍然致命**：fragment 是 mesh 生成的 ⇒ 哪里没有 mesh，哪里连一个 fragment 都没有，往回步进也救不回来。这正是 `reach=1` 现在真正的理由（那 2/212 条方向是**粗场超阈而网格上没有面**，是整块没有几何，不是位置偏）⇒ **`reach` 保留，但理由从"为了包住"改成"为了不漏峰"**；mesh 仍必须**闭合**。
- **步进栅格必须锚在壳/体积上（绝对），不能跟着 fragment 落点走**：换了起点就换了采样相位，找到的交点会差最多一步 ⇒ 判据从"逐字节相同"退化成"Δ 像素"。保住判据的做法：代理只决定**从哪个下标开始扫**，扫描仍走那套绝对栅格、并且可以双向 —— 这样往回补的采样点与今天全量 march 采到的**逐位是同一批**。

一句话：**代理从"必须包住的外壳"降级为"给我一个起点 + 一片可以剔除的空区域"，而步进栅格保持绝对。**

⚠ **与「不烘体」的关系（已更正）**：§25 那条**不是不变式，只是当时不需要**。marching cubes 需要一个 **3D 标量网格**，而这个网格与它产出的 mesh **都是 PCG 的产物、都要进 PCG 缓存**（键 = 内容，§17.1）：改等值面 / 外扩量 / MC 参数时复用同一张网格，改网格参数时复用同一份 mesh。它**不参与着色**（只用来收窄步进范围），所以"丢解析导致后续精度掉"那条顾虑在这里不成立 —— 精度不足由外扩量吸收。裁决记录见 `01-decisions.md` 的 §25 条目。

### §51.12 仪器坏了一半：在飞帧数无界 ⇒ 2240×1400 的数作废、待重测

**症状**：2240×1400 + 有云，显存线性涨 **142–157 MiB/s**，到 6 GB 就 `0x887A0005`；无云档与 480×300 平。

**根因（分配器报告为证，不是猜）**：**不是**每帧新建画布尺寸的纹理 —— 资产计数全程平（`Image 14｜Mesh 7｜Shader 160｜CloudsMaterial 1｜PlanetCloud 1`），画布纹理全是 `× 1`。是**在飞帧数无界**：wgpu 要等一次提交**退役**才回收那一帧的临时资源（`wgpu-core-29.0.4/src/indirect_validation/draw.rs:34` 固定 1 MiB 缓冲，池子只在 `impl Drop for DrawResources`（`draw.rs:771`）归还），而 `--fps` 的 `run_loop(Duration::ZERO)`（无窗口）**没有任何背压** ⇒ CPU 无限跑在 GPU 前面。**71% 的泄漏**是 `Indirect draw validation {metadata,destination} buffer`（各 **1.00 MiB × 1596 笔**）。

- **代理档的射线平均仍走 ~47/56 步**（`(47.06−16.16)/0.66`，佐证：`proxy − proxy_allmiss = −5.98`）⇒ 代理现在的收益**全部**来自"少一批射线"（全 miss −25.33 ≈ 真实场景 −23.74），**不来自"落点更近"**。原因：代理烘的是 `coarse = shape_of(cover, altitude, 1.0)`（**细节取 1 的上界**），而真表面 `final = coarse · detail` 在**里面很深**。

- **零新实现就能拿的**：`bound + proxy` 同时开 ⇒ **70.80 → 36.43 ms（−48.5%）**，云净成本 54.64 → 20.27。
- **并列第二**：降 `steps`（真参数、零实现）56→28 = **−43.8%**（39.77），代价是画面真变。
- **不建议**：优化梯度（天花板 2.08 ms）；云壳镶嵌降级（壳 1 步就在地板 ⇒ 顶点不是瓶颈）。

**仪器自证两条**（这批数能不能信，靠这两条）：

#### §51.14.1 ⚠ 更正：「细代理」是个弯路，方向与设计相反（用户指出）

**设计本来是这样**：**mesh = 粗代理**（由 `coarse = shape_of(cover, altitude, 1.0)` 烘的**外接**代理，包住真表面 ⇒ 覆盖安全，用来做剔除/加速）；**细节 = shader 里解析求值的噪声场**（`billows`，`final = coarse · detail`）。**细节不属于 mesh。**

§51.13 末尾"下一个该实现的：把代理的标量场从 `coarse` 换成含细节的真场 `final`"是**错的建议**，§51.14 那一整段"细代理"就是照它做的 —— 等于**把本该解析求值的细节烘进网格**。它不配叫"代理"：它是"用网格表示真实表面"。

**数字判它死刑**：

| | 中位 | 三角形 | 产物 | 烘 | 覆盖 |
|---|---|---|---|---|---|
| **粗代理 + `bound`** | **36.43 ms** | 58K | 6.6 MB | 0.15 s | **安全**（包住） |
| 真场 mesh（所谓"细代理"） | 36.51 ms | 524K | 39 MB | 21 s | **轮廓丢一圈云**（硬失败） |

**在噪声内打平，但贵约 10 倍、且破坏覆盖。** 根因是结构性的：**网格无法精确表示解析等值面**（外边界余量 −0.0017 ≈ 0.19 px 就是这么来的）⇒ 想靠 mesh 承载细节，就必然在轮廓丢片；补它只能几何外扩，而那是在给一个不该存在的网格打补丁。⇒ **`field=final` 这条留着当已排除的选项（记录在此），不再继续投入**；轮廓丢片的修复工作已中止。

**仍然成立、且是正确方向的两条**：`coarse + bound` 的 36.43 ms（覆盖安全）；以及 §51.14 里量出来的两笔真实开销 —— **22% 的 fragment 擦面而过照旧走 32 步**（~7.6 ms）与**命中像素的解析梯度/着色/透明混合 ~10 ms**（与几何无关）。下一步该从这两笔里找，而不是从 mesh 里找。

### §51.15 细节噪声开次方根（`detail_curve(b) = √b`）—— 稀疏性降 30%，帧时间降 10–18%

⚠ 口径受限（§51.18）：这里的 −10~18% 是窗口中位口径，未用 GPU 口径复取。原文保留。

**诊断（用户）**：硬表面云有 22% 的 fragment **擦面而过**（沿线 32 个采样一次都没超过 `surface_level`，走到栅格末端才放弃）；根因**不是步长**，而是**细节噪声场太稀疏**（值压低位、峰窄）⇒ 阈值以上只有零星峰，离散步长容易跨过去。
**修法**：给细节场（`billows` 那个 5 八度混合）加一次**凹重映射** `detail_curve(b) = √b`，解析梯度按链式法则乘 `detail_curve_slope(b) = 0.5/√b`（WGSL 的 `billows`/`billows_along` 与 Rust 参照场 `px_verify::cloud_field::billows` 两侧同步；Rust 侧走 `Dual` 自动带链式法则）。

### §51.16 软云档的"银边"是**回退分支**造成的台阶，不是几何（含一条可复用的教训）

**症状**：`orbit-soft` 云块轮廓有一圈亮边；剖面 `45 222 170 164 117 219 41` —— 边 222/219 与体内 117–170 之间是 **100 多级的台阶、1–3 px 宽**（硬表面那条路白边更强：4 px 全 ≥219）。

**三选一的裁决（CPU 参照场逐像素诊断，25 条扫描线 6408 个有云像素）**：

- **(B) 场被截断：证伪** —— 壳边界 48,400 方向 × 6 个海拔，场值最大 **0.000826**（τ=0.20），高于 τ 的 **0 个**；等值面只出现在海拔 0.03–0.73，**闭合在壳内部**。
- **(A) 几何：成立，但解释不了台阶** —— 有法线的 458 个轮廓点海拔 0.035–0.69、raw 刚过 τ、无夹取饱和。⚠ 而且它给了一个反直觉的补充：**这个场的法线以径向为主**（`|g·r̂|/|g|` 中位 **0.75**，内部 0.98），所以"轮廓 = 相切处 N⊥视线"在像素级**并不典型**。
- **(C) 回退分支：就是那条边** —— `have_surface` 只在 `optical >= SOFT_TAU/extinction` 时置真，而**掠射的轮廓射线积累不到这个光深** ⇒ `surface_lit = 1.0`、`surface_self_shadow = 1.0` ⇒ **`soft_shade ≡ 1.000`（全亮）**。轮廓带 785 px 里 **41.7% 落回退**（内部只 0.8%）；回退像素 alpha 上界 `1−e^−2 = 0.8647` ⇒ **220.5/255**，与观测的 222/219 吻合。
- **连续性判据（决定性）**：跨"有/没法线"边界的 `Δshade` 中位 **0.856**（≈最大值 1.0→0.14），同分支内仅 **0.017**（**差 50 倍**）⇒ 是**台阶**，连续法线场不可能产生。实例 y=240：x=929 体内 35.6 → x=930 回退 **217.7**。
- **(D) `(1−密度)` 极性：放大器不是源头** —— 体内密度→1 ⇒ `shaped = 0.5` ⇒ shade 上限只有 **0.57（145/255）**；轮廓处密度≈0.35 ⇒ N·L=1 时 shade 可到 1.0。0.86 的台阶全部来自 (C)，(D) 决定邻格越暗、回退格越刺眼（增亮 88–187/255）。

**根因是我的设计错误**：我建议"每条射线只算一次法线、在 ≈86% 不透明那一层算"。掠射射线**永远到不了那一层** ⇒ "有没有法线"变成了硬判据 ⇒ 它自己就是那圈边。

**教训（可复用）**：**别拿"某个累积量达到阈值"来开关一个逐像素的属性**（法线、着色分支、LOD…）—— 累积量在掠射/边缘射线上天然到不了阈值，于是属性会在一条**与几何无关**的曲线上突变。要开关，就用**到处都存在的判据**（例如该射线密度最大的采样点、或第一次穿过 τ），累积量只用来**加权**，不用来**开关**。

### §51.17 软云档改成"每步采样法线 + 每步估自阴影"：银边结构性消失，且**更快**

⚠ "更快"未经 GPU 口径验证（旧软档 vs 新软档的配对没做）；"用户感到变慢"的主因是后端被换（§51.19/§51.20）。原文保留。

**改法**（只动 `art/shaders/clouds.wgsl`，硬表面路/`bound`/粗代理/`reach`/`gradient` 选档一行未动；diff 125+/47−）：
- **删开关**：`SOFT_TAU` / `tau_visible` / `have_surface` / `surface_lit` / `surface_self_shadow` 全删（grep 计数 0）⇒ **"有没有法线"这个概念在代码里不存在**，于是 §51.16 那条回退分支**结构上不可能存在**。
- **每步**：`visible = 1−exp(−σ·ds·ext)`；`normal = soft_step_normal(...)`；`lit = mix(1, 0.14+0.86·clamp(N·L,0,1), shadow)`；`lit_sum += T·visible·lit; T *= 1−visible`；最后 `soft_shade = clamp(lit_sum/max(alpha,1e-6),0,1)`。⇒ 值域**自动**落在硬表面那条 Lambert 的 `[0.14, 1]`；`(1−密度)` 与"像素 alpha 当 shadow_depth"两条一起退休（**§51.16 的 (D) 也一并消失**）。
- **每步法线 = 便宜的复合**：`∂shape/∂altitude`（解析、径向）+ `∂shape/∂cover · ∇cover`（**切向**，而 `∇cover` 就是场景里**本来就有**的 `slope_x/y/z`，与 coverage 一起打在**同一张立方图的 `.gba`**）⇒ **与循环里那次 `textureSampleLevel` 同一次采样白拿**、0 次额外立方图采样、0 次额外噪声采样。**主动丢掉** `∂shape/∂noise·∇noise`（要 5 八度梯度噪声）。

**判据**：

| 判据 | 改前 → 改后 |
|---|---|
| 台阶（shade 场，10415 对旧回退边界、两端都不贴外轮廓） | 中位 **0.8587 → 0.0188**；改前 min=中位=p90=max **全是 0.8587**（常量分支的指纹，= 1.0−0.1413）；同分支比值 **58.6× → 2.20×** |

| 扫描线剖面（y=831） | `… 207 **236** \| 102 102 …` → `… 162 164 **160** \| 151 135 117 …` ⇒ 跳变变成**平滑峰** |
| 看图 | 那条 1–3 px **亮白描边消失**；软羽化、实、法线自阴影三条都在；体内不再被压到 0.57 上限 |

**溢价的原因判明（结论）**：旧软档那笔溢价就是**每像素一次** `cloud_field_gradient_analytic`（2×5 八度 `fbm_3_grad`）；新设计换成**每步便宜算术**后溢价归零 ⇒ **"每步采样"这个更对的口径顺带更快**（现在解析梯度只剩硬表面路一处调用）。

**两个更正**：

1. **§51.16 里"220.5 与 222/219 吻合"是巧合** —— 回退像素 alpha 实测上界 **239/255，即 sRGB 编码后的 0.8647**（目标本来就是 sRGB 编码）。结论（回退分支造成台阶）不变。
2. **残差没归零**：改后那批旧边界对上仍有尾巴（p90 0.1227、最狠 shade 207→105），落点在 **1–4 px 宽的细丝/掠射薄片**上（可见链只有两三个采样、法线本就转得快），**不是分支开关**。连续银边已消失。

**每步全解析梯度那版**（另烘一档）：可编译、能出云，但**管线编译 ≫2 s**（40 帧等待窗里那张图**逐字节等于无云**，等 90 s 才对）⇒ **运行帧时间未测**。质量差（复合法线 vs 全解析，在"第一个 raw>τ 的点"同口径逐像素比）：轮廓带夹角 **中位 26°/均值 32°/最大 172°**，`|Δ(N·L)|` 均值 **0.175**，`0.86|Δ(N·L)|>0.05` 的带内像素占 **6.3%**（内部夹角中位 20°）⇒ **差异明显，换不换属美术取舍**。

### §51.18 ⚠ 口径更正：app 循环的**逐帧中位**不能当每帧成本（差值符号会反）—— 一律用 GPU 时间戳

> **规则与权威版本在 `09-instruments.md` §57（「三件必须在报告里读到口径的事」第 1 条）与 §58.1（配对差表）**；本节只留「一句铁律 + 本文件适用的实测证据」。
> **去重说明**：原来写在这里的规则陈述、「魔数退休清单」「"稳定"是事件不是时间」「GPU 采样不是每帧一条」已与 `09-instruments.md` §57/§58.1 合并，**权威版在那边**；本节实测表原样保留。

**一句铁律**：判据一律读 `pair.gpu_delta_ms`（GPU 时间戳 p50 的配对差）；app 逐帧序列是 `gpu_backpressure` 造出的双峰伪影、**中位落在便宜的那几帧上 ⇒ 符号会反**。

**事实**（协议 v11 实测，信号表见 `09-instruments.md` §58）：`gpu_backpressure` 每 4 帧 `poll(wait_indefinitely)` ⇒ **app 逐帧序列双峰**（13 ms ×3 + 135 ms ×1）⇒ app **中位**落在便宜的那三帧上。配对差（被测档 − `orbit-bare`）：

| 档 | app **中位**差 | app 均值差 | **GPU p50 差** |
|---|---|---|---|
| `orbit` | **−1.33 ± 1.27** | 30.25 | **+38.68** |
| `orbit-proxy` | **−0.70 ± 1.47** | 23.77 | **+32.15** |
| `orbit-soft` | **−1.53 ± 1.76** | 32.82 | **+41.10** |
| `orbit-surface` | **−1.83 ± 3.05** | 45.37 | **+52.86** |

⇒ 按 app 中位读，"有云"比"无云"**还便宜**；真值是**贵 32–53 ms**。**这是仪器自伤，不是机器问题。**

**对本文件其余各节的效力**：§51.x 里凡按"窗口/逐帧中位帧时间"给出的绝对值与百分比（§51.11 / §51.13 / §51.15 / §51.17）**不得再当每帧成本**，要精确引用须按 GPU 口径重取；均值口径可作旁证（实测 app 均值 ≈ GPU 时间，如 soft 32.82 vs GPU 41.10、surface 45.37 vs 52.86）。协议 v11 的 `PerfReport` 同时给 app 中位/均值/分位数与 `gpu_ms`，外加 `pair{gpu_delta_ms}` —— **判断只用 `gpu_delta_ms`**。

### §51.19 用户感到"同一份云变慢"的主因是**后端被换了：Vulkan → DX12**（我们自己的 harness 泄漏了环境变量）

⚠ 本节是 DX12 记录（保留）；产品口径看 §51.20 的 Vulkan 表。

**单变量实验**（同一新 exe、同一场景 `orbit-soft`、同一 shader `d9a3ea0c4d75`、同一 2240×1400 窗口，**只改 `WGPU_BACKEND`**）：

| 运行 | 后端 | 帧周期 | fps | worst |
|---|---|---|---|---|
| 旧 exe（21:17 构建） | Vulkan | **14.9 ms** | 66.9 | 18.8 |
| 新 exe | Vulkan | **17.5 ms** | 57.1 | 23.7 |
| 新 exe + `WGPU_BACKEND=dx12` | **Dx12** | **40.1 ms** | 25.0 | **85.3** |

⇒ **DX12 比 Vulkan 慢 2.3×、长尾 3.6×**；同一后端下**新旧 exe 只差 +2.6 ms（+17%，n=1，未坐实）**。

**后端为什么会变**：`tools/harness.ps1:29` **无条件 `$env:WGPU_BACKEND='dx12'`** ⇒ 任何 dot-source 过它的 shell 里起的 viewer 都继承 dx12。证据：pid 11028 的 stderr 是 `backend: Dx12`，而**更早所有 viewer 的 stderr 全是 `backend=Vulkan`** ⇒ 用户"以前"看到的窗口**都是 Vulkan**，观感完全对得上。（DX12 那条路另有 6 次 `ResizeBuffers failed 0x887A0001` / `window is in use` 的独有失败模式。）

⚠⚠ **两条比这个 bug 更重要的结论**：

1. **环境变量必须只作用于被测/被看进程**（传进子进程的环境），**不许在 dot-source 的脚本里全局改 `$env:`** —— 否则"测量工具"会静默改掉**产品实际走的路径**。这与本会话早先那几起（管道/编译/锁 exe）是同一类：**工具的手伸出了自己的边界**。
2. **测量的后端必须与产品的后端一致**。我们**所有测量一直在 DX12**（会话环境里就设着），而**viewer（= 用户拿到手的默认体验）一直在 Vulkan** ⇒ 我们这一整轮优化的是**用户没看到的那条路**；反过来，**仅仅换后端就有 2.3× 的空间**。⇒ 必须先定"产品目标后端是哪个"，再谈优化。

**同一后端（DX12）下的四档 GPU 真数**（协议 v11，判据 `pair.gpu_delta_ms`，参照 `orbit-bare`）：

| 档 | GPU p50 | GPU p99 | app 均值 | gpu_delta_ms |
|---|---|---|---|---|
| `orbit-bare` | 0.61–0.66 | 0.64–0.85 | 14.7–14.9 | 0 |
| `orbit-proxy` | **32.42** | 37.84 | 38.97 | **+31.81 ± 1.16** |
| `orbit-soft` | **39.85** | 41.32 | 46.55 | **+39.23 ± 2.47** |
| `orbit`（体积） | 39.47 | 41.29 | 45.41 | **+38.75 ± 2.30** |
| `orbit-surface` | 52.72 | 63.32 | 59.69 | **+52.10 ± 3.11** |

⇒ **代理路仍是最省的云路**（+31.81）；**软档（+39.23）≈ 体积路（+38.75）**、比硬表面球壳（+52.10）便宜；软档比代理贵 **+7.4 ms（+22.9%）**。

**每帧系统对照（`view()` vs `serve()`）**：`watch_pipelines` **两边都跑**（每帧遍历 46 条 `CachedPipelineState`，**1–5 µs/帧 ≈ 0.03%**，解释不了任何差）；viewer 独有那些（相机、按键、`poll_request` 读 json、心跳、标题、FPS 读数…）全在 µs 量级；`RenderDiagnosticsPlugin` **不在 viewer**（只有 serve 有）⇒ 用户窗口没有时间戳开销。**app 版本本身的回归 ≤ +2.6 ms 且未坐实。**

**跨进程管线缓存（只调研）结论：本机不值得做，等上游。**
- wgpu 29 有 `Device::create_pipeline_cache(&PipelineCacheDescriptor{fallback,data})` + `PipelineCache::get_data()`，但 **feature `PIPELINE_CACHE` 的文档明写 `Unimplemented: DX12, Metal`**；映射实测：**Vulkan 真用 `VkPipelineCache`**；**DX12 完全 no-op**（`wgpu-hal/src/dx12/device.rs:2214` 忽略 desc、`get_data` 走默认 `None`，全仓零命中 `ID3D12PipelineLibrary`；DX12 自带的 `ShaderCache` 是**进程内 200 条上限、不落盘**）。
- **Bevy 0.19.1 一行都没接**（0 命中）；唯一缝隙是 `RenderDevice::create_render_pipeline / create_compute_pipeline`（`render_device.rs:188/195`，两处 `cache: None`），**必须 fork/vendor `bevy_render`**。
- **上游已有**：[bevy#19809](https://github.com/bevyengine/bevy/pull/19809)（OPEN，Vulkan-only 门控，正是我们要的）；[wgpu#8526](https://github.com/gfx-rs/wgpu/issues/8526)（DX12/Metal，OPEN）。⇒ **别自己造**。另注意风险：不启 feature 调它会 validation error ⇒ Bevy 默认 `AppExit::error()`（harness 判硬失败）；硬塞 feature 则 `request_device(...).unwrap()` panic。
- 唯一可能受益的场景是 **Vulkan**（viewer 默认后端），但 wgpu 自己承认大多数桌面驱动已有自己的缓存 ⇒ 收益不确定，代价仍是 fork。

### §51.20 后端锁死 Vulkan（两层）+ Vulkan 四档表（**取代 §51.19 的 DX12 数作为产品口径**）+ 驱动缓存实测

**锁死（两层，且都验过）**：
- **代码**：`px_render/src/main.rs` 新增 `wgpu_settings()` / `render_plugin()`，`backends: Some(Backends::VULKAN)`，`serve()` 与 `view()` **两处**都 `.set(render_plugin())`（`show()` 不建 App/不建设备，无需改）。
- **环境变量盖不过它（查清了路径）**：Bevy 只在 `bevy_render-0.19.1/src/settings.rs:84`（`impl Default for WgpuSettings`）读 `WGPU_BACKEND`（`wgpu-types-29.0.4/src/backend.rs:156`），而 `InstanceDescriptor::from_env_or_default()` 在 wgpu/bevy 全仓**零命中** ⇒ 显式给结构体即锁住。**实测**：父进程故意 `WGPU_BACKEND=dx12`，子进程仍 `后端：Vulkan｜驱动 NVIDIA 596.36` ✓
- **会失败的门**：`assert_vulkan_backend()` 在 Startup 打印实际后端，非 Vulkan ⇒ `exit(2)`（样例：`后端断言失败：实际 Dx12，要求 Vulkan（WGPU_BACKEND=Some("dx12")）—— 后端决定帧时间量级，不许静默换`）；harness fail-fast **1.15 s 判失败**（不是 180 s 超时）。配套 `clear_own_lease()`：`serve` **写完租约才起 app** ⇒ 断言失败直接退出会留**陈旧租约**、让下一次合法启动被单例闸拦成**假故障**（实测踩到）。
- **工具侧**：`tools/harness.ps1` 删掉全局 `$env:WGPU_BACKEND='dx12'`（那正是"同一份云突然变慢"的成因），改成 `Start-Process -Environment` 只作用于子进程 + `Invoke-Client` 用 try/finally 设置并还原；全仓扫描**只有那一处**设过它；`tools/probe.ps1` 已改走 `Invoke-Client`。
- ⚠ **一般教训**：**测量工具不许改产品走的路径**（环境变量必须只作用于被测/被看进程）。这与本会话其余几起同族（管道、锁 exe、编译），但这条最隐蔽 —— 它改的是**渲染后端**，于是量出来的和看到的不是同一条路。

**Vulkan 四档表**（协议 v11 stable、2240×1400、60 帧、参照 `orbit-bare`、判据 `gpu_delta_ms`）：

| 档 | GPU p50 | GPU p99 | app 均值 | gpu_delta | （DX12 对照） |
|---|---|---|---|---|---|
| `orbit-bare` | 0.56 | 0.57 | 14.90 | 0 | 0 |
| `orbit-proxy` | 10.88 | 11.23 | 18.10 | **+10.04** | +31.81 |
| `orbit-soft` | 14.10 | 14.72 | 17.86 | **+13.43** | +39.23 |
| `orbit`（体积） | 13.92 | 14.54 | 17.62 | +13.36 | +38.75 |
| `orbit-surface` | 17.65 | 18.56 | 22.56 | **+17.08** | +52.10 |

- **云的成本整体缩到约 1/3**（每个 delta 小 2.9–3.2×）。
- **"代理是最省的云路"在 Vulkan 上仍成立且优势更明显**：`soft − proxy` 从 DX12 的 +7.4 ms（+22.9%）降到 **+3.29 ms**，但**相对占比升到 +30.2%**。
- ⚠ **天花板挪位（重要）**：Vulkan 下**所有云档的 app p50 都压在 ~14.0–14.6 ms**，而 GPU p50 只有 10.9–17.65 ⇒ 这个窗口尺寸下云路**已不太卡在 GPU 上**；**DX12 时代那些按 GPU 毫秒算的百分比改进，在 Vulkan 下对应的余量小得多 ⇒ 优化判断需重做。**
- **仪器文档补充**：**Vulkan 下 app p50 不区分档位**（全是 ~14 ms），只有 GPU 口径能分辨；app 均值仍可作旁证（随档位单调）。

**驱动缓存 / 管线缓存实测（结论：不改源码接不了，且不值得）**：新进程→就绪中位 **2 959 ms**；冷"等管线" 9 次 = 214–304、**中位 223 ms**（47 条 ≈3.4 ms/条）；同进程热地板 **中位 61 ms** ⇒ **净编译+创建 ≈162 ms = 一次冷请求的 7.6%、稳态 0 ms**。
- **序列完全不下降**（这份 shader 当天已编过很多次 ⇒ 驱动缓存本就热），跑前跑后 `%LOCALAPPDATA%\NVIDIA\{DXCache,GLCache}` **978 个文件时间戳一个没变** ⇒ 驱动缓存没有拿掉这块。
- **wgpu 全栈没有任何**管线缓存相关的环境变量（清单已列全）；app 侧要用只能 `Device::create_pipeline_cache` + `PipelineCacheDescriptor{fallback,data}`，而**必须把 cache 传进 `RenderPipelineDescriptor.cache`**，那两处由 `bevy_render` 写死 `None`（`render_resource/pipeline_cache.rs:565` 渲染 / `:623` 计算）⇒ **应用侧无接口，只能 fork `bevy_render` 或等上游**。
- ⇒ **不值得 fork**：上界 162 ms/新进程（7.6% 冷、0 稳态）；等 [bevy#19809](https://github.com/bevyengine/bevy/pull/19809)。

**遗留**：`px_probe/src/common.rs` 仍默认 DX12（同类地雷，未改）；`frame-probe.ps1` 的 stable 路热身只用 `orbit-bare`（无云）⇒ **第一个带云的档要付真 shader 首编**（这是那次 `orbit-proxy` p99=22.67 的来源，`Invoke-ScenePhase` 已经按"带云最多的档"热身，stable 这条没有）。

## §59 软档收"别人的影" ＋ 地表云影（自写 surface material）

> 用户 2026-09 的两条要求，以及为定口径问到第三次才问清的那几个点：**①** 软云要**接收他物**
> 投下的影（"它人阴影"），自己的自阴影**继续**走每步法线的 N·L；**②** 星球表面要有**粗略的、
> 柔和的**云影，它是"表面着色器里一条相对独立的特性"——**软采样一张指定高度的云 cubemap**。
> 两次追问里被否掉的路线也记在下面（"新烘一张专用 shadow cubemap"、"云壳当 caster"）。

### §59.1 云收别人的影 = 采样 Bevy 的 shadow map

- **口径**（用户裁决）：云收的是**别人**（山尖、环）的影。云自己的自阴影还是 §51.17 那条
  每步 `N·L`（`lit = mix(1, 0.14+0.86·facing, shadow)`），**不新增第二次覆盖度采样**。
- 改法：软分支循环里每步多一句 `cast_shadow = fetch_directional_shadow(0u, point, normal, point_view_z, in.position.xy)`，
  `lit_sum += T · visible · lit · cast_shadow`（`point_view_z` 由 `view.view_from_world` 现算）。
- **没有新开关**：没开阴影的场景里 `num_cascades == 0`，那个函数按构造返回 1.0
  （`get_cascade_index` 直接返回 0、再 `0 >= num_cascades` 越界返回 1.0）⇒ 不需要为它加 uniform。
  实测：`orbit-soft-plain`（`shadows = 0`）与**改之前那张基线图**在云上**一个像素都不差**
  （差异图里云全黑，见 §59.3）。
- 场景侧（三个新旋钮都缺省成老行为，见 §59.4）：
  - `shadows`（planet part，缺省 0）= `DirectionalLight.shadow_maps_enabled`；
  - 级联**按这颗行星定**：`num_cascades 2 / minimum_distance 0.1 / first_cascade_far_bound 2.5 / maximum_distance 6.0`
    —— 评审相机距离是 3.15 与 1.40，而 Bevy 缺省是 `0.1..150`，那样一个 texel 覆盖半颗星球。
  - **云壳与大气壳都挂 `NotShadowCaster`**：它们是透明的一整颗球，进了 shadow map 就是一颗
    **球形的硬影**（云影会变成"整颗行星都在影子里"）。⚠ 这一条不做的话，本项与 §59.2 会同时坏掉。

### §59.2 地表云影 = 自写 surface material ＋ 覆盖度 cubemap 的解析查询

- **为什么必须自写材质**：`StandardMaterial` 两条路都没有"只压直接光"的位置 ——
  `diffuse_occlusion` 只吃间接光，直接光那一项在 `apply_pbr_lighting` 里直接乘了阴影贴图的结果。
  ⇒ `surface` 槽从 `BUILTIN_SLOTS` 挪进 `WGSL_SLOTS`（`slots.rs` 现在**没有**内建槽了），
  新增 `art/shaders/surface.wgsl` ＋ `px_render/src/surface.rs`（`SurfaceMaterial`，
  版本身份/占位/特化键与云、大气同一条规矩）。
- **云影怎么查**（用户口径："用近似解析解求与太阳方向切向分量乘以 h 对采样的偏置"）：
  `t = −b + √(b² + r² − |p|²)`（b = p·s、r = 云带指定高度的半径）拿到穿过的步长，
  方向只搬**切向**那一份：`probe = normalize(d + (s − (s·d)d)·t)`，再在半影轴 ±`0.045`
  取三个方向平均（**软**），`shadow = 1 − strength·(1 − e^{−cover·2.0})`。
- **只压直接光**：间接光（环境光）那一支**不乘** `cloud`/`cast_shadow` —— 云挡的是太阳，不是天光。
- 换材质本身的代价：直接光的**高光那一项**丢掉了（漫反射的 `Fd_Burley`、`F_AB`/`EnvBRDFApprox`
  的环境光那一支都逐字对齐 `bevy_pbr`）。差异带见 §59.3。
- ⚠ **太阳有"两份"**：云影那条路用的是 shader 常量 `SUN_DIRECTION`（`common.wgsl`），
  阴影贴图与直接光用的是场景里那盏 `DirectionalLight` 的 `direction_to_light`。现在两者相同
  （灯位 `(-4.2, 1.15, 2.35)` 归一化后与常量前四位一致），但**改灯不动常量就会分叉**：
  云和云影跟着常量走、山的影子跟着灯走。这是仓里早就有的重复（云一直这么算），
  这次没有合并 —— 要合并得让 `SUN_DIRECTION` 变成材质 uniform 或从灯里读。
- ⚠⚠ **`view.exposure` 必须自己乘**：Bevy 把曝光乘在 `apply_pbr_lighting` 的总光里
  （`pbr_functions.wgsl:864`），自写材质不乘就是**亮三个数量级**（`Exposure::default()` = EV100 9.7
  ⇒ ≈ 1e-3）。第一版就是这么出的：整颗行星纯白、颜色全丢 —— 而**所有门都是绿的**
  （管线 0 失败、判据图有云、字节数正常）。这正是 §51.1 那类"看起来在测"的坑，只是这次错的是外观。
  ⚠ 反过来看：本仓**已有的**两个自写材质（云、大气）都没乘曝光 ⇒ 它们本来就偏亮
  （云的"均匀白"有一部分是这么来的）。**这次没动它们**（用户只要求软档的这两条），
  要不要给云也补曝光是另一个待决问题。

## §61 细节随时间动：两层风 ＋ shader 内的时钟

> 用户口径（2026-09-15）：**"让细节随着 noise 场时间变化而变化，用 shader 内时间，
> 不要逻辑帧注入"**；追问后定为 **"分两层、不同风速"**、缺省关（做成场景参数）。

### §61.1 怎么做

- **时间从哪来**：`globals.time`（Bevy 的 Globals uniform，group 0 binding 11，渲染侧每帧自己写）。
  **不经逻辑帧注入** —— P31 删掉"按逻辑帧推进的自转"就是因为那条路同时毁掉可复现性与帧间一致性；
  这里要动的是**着色细节**，不是场景状态，所以走 shader 自己那只钟。
- **动哪一层**：`billows` 的两层噪声（tower 3 个八度 / skin 2 个八度）各自的采样方向加一份偏置，
  两层的**时间尺度写在 WGSL 里且故意不同**（0.13 与 0.37 rad/s ⇒ 周期约 48 s 与 17 s）⇒
  细的那层在粗的那层上滑过去 = 翻涌/搓动；同速就只是整块平移。
  场景给的是**幅度**（`wind` / `wind_skin`）。覆盖度立方图**不动** —— 地表云影查的是同一张图，
  让它动就得两边同步（§§59 那条"一份内容两处用"的坑）。
- **为什么是有界正弦而不是"速度 × 时间"**：线性漂移下采样点一直往外走，
  挂半小时后常数项盖过方向项 ⇒ 整颗球的细节被抹成一片（而且回不来）。
  正弦还有个好性质：`t = 0` 时偏置为 0 ⇒ 第一帧与静态那张图逐位相同。
- **解析梯度仍然精确**：偏置是**常量向量**（只随全局时间变，不随方向/位置变）⇒
  `∂p/∂direction` 一个字没变，`billows_along` 里那套链式法则/切向-径向分解照旧成立。
  ⚠ 换成"随时间旋转方向"就要在梯度那边再乘一个 `R⁻¹`（`rotate_vector`），
  否则法线会慢慢跟轮廓错开 —— 这是选正弦而不是旋转的原因。
- 细节风的偏置用 `var<private>` 存（片段入点第一句 `arm_wind()` 算好，`billows` 里读）：
  `billows` 有 4 个调用者，其中一个是**探针的 compute 入点**，而探针的 bind group 0/1 是空的
  ⇒ 让 `billows` 自己去读 `globals` 会把探针打挂。私有变量按 invocation 一份，探针不碰它
  ⇒ 探针看到的风恒为 0。

### §61.2 参数与缺省

| 位置 | 名字 | 缺省 | 含义 |
|---|---|---|---|
| clouds part | `wind` | 0 | tower 层的幅度（方向单位；0 = 不动） |
| clouds part | `wind_skin` | 0 | skin 层的幅度（两层时间尺度不同 ⇒ 差个符号就搓起来） |

`orbit-soft-wind`（`wind = 0.15` / `wind_skin = -0.26`）是唯一的演示档；
判据/对账请用不带动画的 `orbit-soft`（缺省 0 ⇒ 与加这个特性之前逐位相同）。

## §63 软档接粗代理几何 ＋ 循环内上界早退（「代理 + 软」）：云净成本 13.83 → 6.87 ms（**−50%**）

> 用户口径（2026-09-15）：**"需要：代理 + 软"** —— 把 `clouds::proxy` 那张粗代理 mesh 接到
> 软云档（`gradient = 2`，§51.17）上；追问后定：**代理要进 `orbit-soft` 本体**（成为软档默认）。
> 活落在 `.worktrees/soft-cloud-perf`（分支 `feature/soft-cloud-perf`）。
> 口径：**Vulkan**（§51.20 代码锁死）+ **GPU p50** + 参照 `orbit-bare` + 协议 v11 + 2240×1400。

### §63.1 怎么接的（代理那条：**渲染侧与 shader 一行没改**）

`orbit-soft.toml` 的 clouds part 加一个成员（与 `orbit-surface` → `orbit-proxy` 同一条路）：

```toml
members = { shader = "shaders::clouds", field = "mixed", slope_x = "slope_x", slope_y = "slope_y", slope_z = "slope_z", proxy = "clouds::proxy" }
```

`planet.rs::spawn_clouds` 只看这个成员在不在（§51.11 那条路，与 `ablate` / `gradient` 无关）
⇒ 装配器把 `ico(64)` 球壳换成 **29,224 顶点 / 58,612 三角形**的代理 mesh。
配对档：`orbit-soft-shell`（两个开关都没有 = §63 之前那一版 `orbit-soft` 的内容）、
`orbit-soft-proxy`（只有代理）。三份的 planet / atmosphere part 逐字相同。

**形状一个字节都不用重烘**：代理的标量场是 `coarse = shape_of(cover, altitude, 1.0)`、`τ = 0.20`、
`inner/outer = 1.01/1.06`、`coverage/base/top/taper/coverage_gain/erode` —— 与这一档的
clouds part **逐项相同**（`art/clouds/coarse.toml` 就是照着它写的）⇒ 现成的
`clouds::proxy@d4dc13fe6bde` 正是这一档的代理。重烘 `planet` / `clouds` 两张图**全部命中**
（15/15，键一个没变）⇒ 没有新烘任何内容。

**覆盖为什么是结构上安全的**（不需要经验外扩）：软档这一步的密度 =
`smoothstep(τ, τ + SOFT_EDGE, shape_of(cover, altitude, billows))`，而 `billows ∈ [0,1]` 且
`shape_of` 对 noise 单调非降 ⇒ `shape_of(..., billows) ≤ shape_of(..., 1.0) = coarse`
⇒ **{软档有云的视线} ⊆ {coarse > τ}** = 代理网格圈起来的那个区域。代理能少掉的只可能是
**本来就没有云**的 fragment。（与 §51.10.2 同一条论证；⚠ 与硬表面那档不同的是，软档**不吃**
"步进栅格锚在壳上"那一套 —— 原因见 §63.4。）

### §63.4 为什么软档只拿回 −13.5%（不是硬表面的 −41%）—— 剩下的杠杆在循环里，不在几何里

**软档的步进与 fragment 落点无关**：`chord = min(hit.exit, scene_distance) − hit.entry`、
`steps = clamp(chord/stride, 16, steps)`、`along = hit.entry + step*0.5` —— 这三个量全由
**射线 + 解析壳**决定，`in.world_position` 只用来定射线方向。所以代理在这条路上**只能剔除
fragment**，一条射线都不会变短（硬表面那条不一样：§51.10.4 的起点下标是 fragment 落点定的）。

**被剔掉的那些 fragment 在软档里本来就很便宜**：它们的每步只做 `medium_of` + `coverage_of`，
`cover <= 0` 就 `continue` —— `billows`（3+2 八度）、`soft_step_normal`、shadow map 采样
**一律没发**（都在密度非零之后）。硬表面那条则每个空走 fragment 都要在 56 步里
**每步调一次 `cloud_field`**（含 `billows`）⇒ 同样的"剔除空区域"，那边值 7 ms，这边只值 1.85 ms。

⇒ 结论与 §51.9/§51.14.1 同向、但落点更具体：**软档的下一刀该切循环内部**（到不了阈值的步
本来什么都不产出），而不是继续在几何/分辨上找。**这一刀就是 §63.6。**

### §63.6 第二条杠杆：软档循环内的保守上界早退（**逐字节不变**，−5.1 ms）

**改哪一行**（`art/shaders/clouds.wgsl`，软分支的步进循环里、算完 `cover` 之后、`billows` 之前）：

```wgsl
if soft && params.bound != 0u && shape_of(cover, medium.altitude, 1.0) <= params.surface_level {
    continue;
}
```

**为什么逐位相同**：`shape_of` 对 noise 单调非降、`billows ∈ [0,1]` ⇒ 真实密度
`shape_of(cover, alt, billows) ≤ shape_of(cover, alt, 1.0) ≤ surface_level` ⇒ 下面那次
`smoothstep(surface_level, surface_level + SOFT_EDGE, …)` **恰为 0** ⇒ `visible = 1 − e⁰ = 0`
⇒ `lit_sum += T·0·… = 0`、`transmittance *= 1.0`（逐位不变）、`optical += 0·step = 0`
⇒ 这一步**本来什么都不产出**。跳过的只有三笔真开销：`billows`（3+2 八度）、
`soft_step_normal`、以及**每步一次 shadow map 采样**。与 §51.7 那个 `bound` 是同一条论证
（这边连"返回 0.0"都不用，直接 `continue`）。

**为什么只挂在 `soft` 与 `params.bound` 上**：体积那条老分支读的是 `field_density` **本身**
（`surface_level` 在那儿不是阈值）⇒ 早退会改像素，它不许拿这条；`params.bound` 缺省 0
⇒ 所有老场景一个像素都不动。

**判据（逐字节，两种分辨率）**：`orbit-soft-proxy` 与 `orbit-soft` 只差 `bound = 1`
（量的时候赢的那一档还叫 `orbit-soft-proxy-bound`；它后来折进本体、文件删了 ——
两者渲染逐字节相同，见 §63.8 的哈希对账）。

| 分辨率 | `orbit-soft-proxy`（无 `bound`） | `orbit-soft`（`bound = 1`） |
|---|---|---|
| 2240×1400 | `04fe9dac8042a721…`（1,258,524 B） | **同一哈希**（同字节数） |
| 480×300 | `0dc9fe248ecfc688…`（107,869 B） | **同一哈希**（同字节数） |

顺带一条**回归**：改 shader 之前那张球壳档（现在的 `orbit-soft-shell`）是
`11b0a659bb71ad47…`（1,257,647 B），改完重出**逐字节相同** ⇒ 这条改动对
所有没写 `bound` 的场景确实是零影响。
⚠ 480×300 那批的 `has_cloud` 报了一次 `False`：**不是丢云** —— 那两张图逐字节相同，
而 `has_cloud` 的参考图是"这一批的第一张"（两张一样 ⇒ 网格差分 0 < 阈值）。
判据图要么把无云档放第一个，要么看哈希（§57 那条 `has_cloud` 口径）。

**帧时间（同一会话、同批、协议 v11、60 帧、两轮、逐轮换序）**：

| 档 | GPU p50（第 1 / 2 轮） | 配对差 vs `orbit-bare` |
|---|---|---|
| `orbit-bare` | 0.67 / 1.08 ⚠ | 0 |
| **`orbit-soft`（代理＋早退）** | **7.54 / 7.53** | **+6.87 / +6.45** |
| `orbit-soft-proxy`（代理） | 12.61 / 12.70 | +11.94 / +12.02 |

⇒ **早退 = 12.61−7.54 / 12.70−7.53 = −5.07 / −5.17 ⇒ 中位 −5.1 ms**（占那一档云成本的 **−40%**）。
⚠ 第 2 轮 `orbit-bare` 那一格量到 1.08（平常 0.67）⇒ 第 2 轮的配对差偏低 0.4 ms，
两轮都列出来。
**仪器自证**：同批重测 `orbit-soft-proxy` = 12.61/12.70，与上一批的 12.58/12.73

## §64 窗口路的「正中心接缝」：**`sun_light` 走 Bevy 聚类网格，远距离时查不到灯**（已定位 + 已修 + 已验证）

> 用户 2026-09-15 报：**"背面光照会出现跳变"**（配窗口截图）。
> 缝是真的：用户那张 3× 放大图里 **row 572 一条 414 px 的连续直线、段内跳变 31 级**。
> **根因**：`sun_light()` 里那条 Bevy 聚类光查询（`view_fragment_cluster_index` + z 切片）在
> **相机拉远**时让大气沿 chord 的 5 个采样点**有一半查不到灯** ⇒ 退回兜底 ⇒ 画面上沿网格边界
> 出现**硬台阶**。**修法**：`light.wgsl::sun_light` 直接取场景那盏灯（`clustered_lights.data[0]`），
> 不问网格。**修完：出图路判据图逐字节不变、默认视角除 OSD 外 0 像素变、用户视角那条台阶消失。**

### §64.1 复现（**必须用这套，否则量出来的数不算**）

### §64.2 根因（探针实测，不是推理）

在同一视角上把 `sun_light` 的返回值和场景那盏灯逐采样点比对（探针返回三个二值通道：

| | 左半 | 右半 |
|---|---|---|
| 5 个采样点**全**拿到那盏灯 | **57%** | **4.4%** |
| 第 1 个采样点所在 cluster"有灯" | 55% | 55% |
| 平均对的比例 | 0.74 | 0.22 |

⇒ **不是"这条路上永远没有灯"，而是"部分采样深度查不到"**：`view_fragment_cluster_index` 既要格子
（x/y 由视口尺寸推）又要 **z 切片**（`view_z_to_z_slice`，把 `log(-view_z)` 量化成层）。相机拉到
`distance = 14` 时采样点的 `view_z ≈ −14`，落在与近处完全不同的切片里，就有一半查不到。
左右两半的**失败率突变**（4.4% 对 57%）正是那条**硬台阶**；落点 x = 1120 = 画面正中心，
因为那正是网格 x 方向的边界。

### §64.3 修法（`px_render/assets/shaders/light.wgsl::sun_light`）

**不问 cluster，直接问场景那盏灯**：`clustered_lights.data[0]`（点光源住在聚类缓冲里，而且
Bevy 把点光源排在前面 ⇒ 只摆一盏灯的渲染器，"最近的一盏"就是这一盏）。
兜底（"没有点光源"才退第 0 盏方向光）**改用颜色判"这格写没写过"**：

```wgsl
if all((*data).color_inverse_square_range.rgb == vec3<f32>(0.0)) { …退回方向光… }
```

⚠ **不能用 `position_radius.w` 判"有没有灯"**：那格**不是 range**（实测对这盏灯读到 0），
拿它当阈值会把有点光源的场景也推进兜底 —— 上一轮那次"整幅受光变了 41.6%"就是这么来的
（出图路兜底 = 那盏遗留的 9000 lx 方向光，"换了个太阳"）。那盏方向光已经删掉（§64.6）。

### §64.5 顺手加的两条**窗口相机请求 API**（复现视角用）
