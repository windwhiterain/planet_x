## 0. 一句话

**轨迹对外一律稠密**（每一行自足、每个字段都在、缺省由 schema 说了算），**底层自动稀疏**
（处于中性值的字段、与父级同值的字段、空集合都可以不写）。读的人不需要知道存储长什么样；
编码/解码**无损**（`decode(encode(v)) == v`，可测），「中性值是什么」只有**一处**声明。

## 1. 为什么现在想这件事：B1 量出来的两处浪费

B1（治理/忠诚中间量）落地后我称了一下字节（`--seed 7 --round 6` 的真投影）：

| 量 | 实测 | 说明 |
| --- | --- | --- |
| `main.jsonl` 每行 | **18127 B**（7 行 126888 B） | B1 之前约 12.8 KB ⇒ B1 让它 **+29%** |
| B1 新增的字节 | **5338 B/行**（势力侧 1685 + 城侧 3653） | 占一行 29.4% |
| 其中 `FactionRow.capital` | **1350 B/行** | 7 个字段平时 **6 个是 `null`**，而它 11/12 的回合无事发生 |
| 其中 `loyalty_target` 的两个**全国同值**项 | 城侧 3653 B 里约 **40%** | `capital_share` / `ideology_penalty` 在同势力**每座城**重复；`ideology_penalty` 还与 `factions[].ideology_loyalty_penalty` 重复 |

**结论**：在稠密面里，「每行自足（读的人不用 join）」与「不重复存」是**直接冲突**的——我上一轮
请用户在 (a)「城行只留逐城项、两个全国项去势力行」与 (b)「`capital` 搬进 `decisions`」之间二选一，
本质就是在这个冲突里选。包装一层，**这个冲突就不必再选**。

## 2. 形状（提案）

```text
写：RoundView（稠密 = 唯一真相，形状一个字都不改）
      ──encode(schema)──▶  稀疏记录（省掉中性字段 / 与父级同值字段 / 空集合）
      ──decode(schema)──▶  RoundView（稠密）
读：所有消费者（Rust 读面 / --derived / main.jsonl 的读者 / kit / web）都只看见稠密面
```

三条「可省」规则（**全部是从 B1 那两个样本反推出来的**，不是凭空设计）：

1. **中性值可省**：字段等于它的中性值（`0` / `1.0` / `null` / `{}` / `[]`）⇒ 不写。
   中性值必须是**每个字段一条声明**、住在 schema 里。这同时是历史上那个坑的解药——
   `flow.jsonl` 说「治理覆盖 0%」而同回合 `metrics` 说 100%（见 `pre-post-unify.md` §1）：
   根因就是**缺省值由每个读者自己编**。一处声明之后，缺键只有一个含义。
2. **与父级同值可省**：城行的字段若与它所属**势力行**同值 ⇒ 不写，读时按 grain 向上查找一层。
   B1 那两个全国项自动消失，而**稠密面依旧每行自足**（读的人不必知道它被省了）。
3. **空集合可省**：`{}` / `[]`（`pre` 里的过程量、没评估的 `capital`）⇒ 不写。

## 3. 必须一起定的事（不然会造出比重复更坏的东西）

1. **稠密化发生在哪一层**：只做 checkpoint（引擎内部）？还是对外的 `main.jsonl` / `idx/*.jsonl`
   也做？——对外流也稀疏化的代价很具体：**用 jq 直接看流的人会看到「这行怎么少了一半键」**。
   要么保留 `--dense`（默认稠密）与 `--raw`（存储原样）两个开关，要么对外流只做规则 3
   （那三样本来就是现状，等于不做）。
2. **中性值一处声明**：`schema.json` 增 per-field `neutral`（Rust 侧同源生成 + 一条一致性测试），
   三个消费者注入同一个值。**绝不允许读者自己写缺省**——那正是老坑的成因。
   ✅ **已落地**（见 §7）。
3. **无损性要能测**：一条 property 测试（长局 `decode(encode(v)) == v`，逐回合）+ 一条
   「稠密面字节 = 本提案之前」的对照。它是这套东西能不能信的**唯一**依据。
4. **别碰写面**：控制面 diff 的 `{}` vs `null` 有它自己的三态语义（`engine-data-plane.md` §7.3），
   再叠一层稀疏规则必然撞车。本提案只管**读面的存储编码**。
5. **`--every` 降采样**：稠密化保证每一行列集一致 ⇒ 顺手解掉「稀疏键让 pandas dtype 逐回合翻」。
6. **digest / 可复现**：digest 读稠密面；编码必须无损，否则等于偷偷改了基线。
7. **可调试性**：稀疏流不好肉眼读 ⇒ `--dense`（默认）/ `--raw`（存储原样）两个开关，文档写明
   **「存储不是契约，稠密面才是契约」**。

## 5. 反面意见与风险（要一起看，别只看收益）

* **两个样本不足以设计通用层**：现在手上只有 `capital` 与 `loyalty_target` 两个 case。按老经验，
  从两个样本抽出来的通用机制**很容易做歪**。笨办法（城行删两个全国项、`capital` 搬进 `decisions`）
  今天就能收掉这两处，等 B4 的逐发计划落地、**第三个样本**到手再做通用层，抽象会稳得多。
* **多一层 = 多一处能漂**：编码器 / 解码器 / schema 三者必须同步；schema 的 `neutral` 与 Rust 的
  `Default` 一旦不一致，就会出现「同一份存储、两个读者两个值」——正是要防的那种失败。
* **省的是字节，付的是耦合**：任何直读 JSONL 的外部工具（jq、别的语言的脚本）都要先实现 decode；
  本仓库的 kit 与 web 可以（它们本来就是代码），散装 jq 用法不行。
* **收益随局长度线性增长**：18127 B/行 × 240 回合 ≈ 4.3 MB；省 29% ≈ 1.3 MB/局。
  值不值，取决于长局轨迹是不是真的被反复搬运（`--every` 已经是另一条降压路）。

## 7. 已落地：中性值所有权（`feature/neutral-values`）

用户裁决「先把中性值这个问题解决了」⇒ 先把这套设计里**唯一必须立刻做对**的那一半做了：
**缺省值的所有权收归一处**。存储稀疏化（省字节那一半）**没动**。

### 7.1 形状

* `src/model/neutral.rs`（新）——唯一声明处：
  * `READ_FACE_NEUTRALS: &[(&str, Neutral)]`：读面（`RoundView`）**每一个叶子字段**的中性值，
    路径口径相对读面根、map/数组的值用 `[]`（如 `factions[].governance_scale`）；
  * `Neutral` 六档：`ZeroInt`（整数 0）/ `Zero`（浮点 0.0）/ `One`（**1.0**——「没有账」不是
    「能力归零」）/ `False` / `Null`（「**没算**」，区别于「算了得 0」）/ `EmptyMap` / `EmptyArray`。
    整数与浮点分开是因为 `serde_json` 区分 `0` 与 `0.0`：给整数列补 `0.0` 会把那一列带成 float
    （lazy 表给 `production` 补 `{}` 是同一条理由）。
  * `value::GOVERNANCE_COVERAGE` / `value::GOVERNANCE_SCALE`：引擎运行时缺省用的**具名常量**
    （值来自这里，`sim::observe` 与 `projection` 不再写字面量 `1.0`）；
  * `schema_section()`：直接生成 `schema.json` 的 `neutral` 段（含一段「缺键按这里补、
    **别自己编缺省**」的说明）。
* `schema.json` 新增 **`neutral`** 段：`{root: "view", description, fields: {路径 → 中性值}}`。

### 7.2 五条守卫（各钉一边）

| 测试 | 钉什么 |
| --- | --- |
| `every_read_face_field_declares_a_neutral` | 用 schemars 遍历读面结构，与声明表**双向集合相等**，且类型严格相容（整数档对 `integer`、浮点档对 `number`）⇒ **加字段不加声明就红** |
| `struct_defaults_equal_the_declared_neutrals` | `RoundView` / `LoyaltyTarget` / `CapitalFlow` 的 `Default` 就是声明的中性值（serde 缺字段走的就是它） |
| `pre_face_process_fields_equal_their_declared_neutral` | **引擎实证**：真实世界里「这一步还没跑」的字段（32 条过程量路径）吐出来的值必须逐字段等于声明 |
| `value_consts_match_the_table` | 具名常量与表同值（常量给人读、表给 schema 读，两者不许漂） |
| `schema_publishes_the_neutral_table` | 发出去的 `schema.json` 段等于本表（发布路径不许漂） |

顺带把两处**真实踩到**的坑记下来（都在写测试时暴露）：
1. **schemars 0.8 会把「`$ref` + 文档注释」包成 `allOf`** —— 不认这层，`decisions` / `capital` /
   `loyalty_target` 三个嵌套结构会被当成叶子（摊出来只有 39 个叶子，表里有 50 个）。
2. **map 容器自己也是叶子**：`factions: {}` / `cities: {}`（空世界）是合法状态，中性值 `{}`；
   只摊 `factions[].x` 会漏掉容器本身。

### 7.3 语义区分（写进模块文档，别搞混）

* **过程量**：中性值既是「读者缺键时的替补」，**也是引擎真会吐出来的值**（这一步没跑/没发生）。
* **观测量**（人口/忠诚/世界总量/价格…）：稠密面里它们**永远在**，中性值只是「万一缺键该怎么读」
  的**定义**（读 0 / 读空），**不是**「一个空世界的观测值」——别拿它当语义断言。守卫 3 的
  `PROCESS_PATHS` 清单就是这条区分在测试里的样子。

### 7.4 kit 也跟着不再自己编缺省

`q.neutral("factions[].governance_scale")` → `1.0`（读 `schema.json` 的 `neutral` 段）；
`view_economy()` 里那些 `1.0` 档全部改成从声明取。`view_loyalty()` 对旧投影（没有 B1 那几列）
给**明确报错**而不是静默补零。

**没做的**：§2 的 encode/decode 那一层、规则 2（与父级同值可省）、规则 3（空集合可省）的存储侧、
`--dense`/`--raw` 开关——见 §8：**这些已经裁决为不做**。B1 那两处浪费改用「笨办法」收掉了（§8.2）。

## 8. 裁决：不做通用稀疏层（2026-10，用户提问「究竟该不该稀疏」）

**结论：不做。中性值声明保留（它买的是「缺键只有一个含义」，不是字节）；那两处浪费直接用
两处约定收掉（§8.2）。** 判据是量出来的。

### 8.1 为什么不做

| 项 | 实测 |
| --- | --- |
| 规则 1/3（中性值、空集合）能省的**全部** | **1350 B/行**，且**几乎全是 `capital` 那一个对象**（9 势力 × 每个 6 个 `null`）；`decisions` 的空数组加起来才 ~40 B |
| 规则 2（与父级同值）能省的 | 1461 B/行（两个全国项 × 22 城） |
| 一行 `main.jsonl` | 18127 B（B1 之后） |

* 拿走 `capital` 之后，「中性值可省」的剩余比例约 **0.3%** ⇒ **这层的收益 ≈ 一个对象的存储位置**，
  而那个对象有更便宜的手术（§8.2）。
* 代价落在最贵的地方：读面有**五个**消费者（Rust 读面、`--derived`、`main.jsonl`、web、kit），
  稀疏存储意味着**每个读取边界都要 decode**——jq 用户（文档里的正统用法）不会实现 decode，
  于是要么对外流保持稠密（那省的只剩 checkpoint），要么把 jq 用法废掉。
* 编解码器 + schema 是**三方**要同步的东西，而「两个读面各说各话」正是这仓库流过的血。
* **真正的字节大头是形状不是稀疏**：每行内联整份 `view`（18127 B × 240 回合 ≈ 4.3 MB）。
  要省该动这里（瘦身 / 懒化 / `--every`）。
* **「大而稀」不是稀疏问题**：B4 的逐发索敌计划不是「一堆 null」，是「大多数回合没有、有的回合
  几百行」——那是「该不该进每回合流」的问题，仓库已有 lazy 表 / derived 表 / 事件流三件套答它。
* 想法本身没错，**是载体不对**：`null` 免费、schema 驱动是**列存**（parquet）的性质。
  换列存那天稀疏白送，不需要手搓编码层。

### 8.2 替代方案（已落地，`feature/capital-decisions`）

| 问题 | 做法 | 依据 |
| --- | --- | --- |
| `capital` 7 字段 6 个 `null`（1350 B/行，11/12 回合无事发生） | 搬进 `RoundDecisions.capital`——**稀疏数组**（`kind="capital"` 的判定行），缺席 = 既没评估也没迁 | 判定数组本来就是「大部分回合无事发生」的家（同 `ShipDecision` 的 `hold`） |
| 两个**按势力算一次**的项在每座城重复 | 城行只留逐城不同的三项（`distance`/`entertainment`/`effective`）；`capital_loyalty_bonus` 与 `ideology_loyalty_penalty` **只在势力行** | 「同一个数只有一个位置」（`pre-post-unify.md` §2 规矩 3） |

实测（同口径：`--seed 7 --round 6`，7 行）：

| 量 | B1 刚落地 | 现在 |
| --- | --- | --- |
| `main.jsonl` 每行 | 18127 B | **15652 B**（−2475，−13.7%） |
| B1 的净新增 | 5338 B/行 | **2485 B/行**（−53%） |
| `capital` 那项 | 1350 B/行 | 30 回合整段 **4185 B**（原来 30 × 1350 ≈ 40500）⇒ **约 1/10** |
| 城侧 `loyalty_target` | 3653 B/行 | **1908 B/行** |

配套：`SCHEMA_VERSION` 15 → 16（只动派生读面）；`decisions` 派生表新增 `kind="capital"` 行；
两张过程量表列跟着挪；kit 的 `view_loyalty()` 把两个全国列 join 回来、`view_economy()["capital"]`
改成从判定表取（`None` = 这一回合既没评估也没迁）。

### 8.3 什么情况下改回这个主意（触发条件）

1. **长期存档/搬运成为真实瓶颈**，且 `--every` 降采样不够用——那时候先动**形状**（别内联整份 view），
   再谈编码。
2. **将来出现一大批默认值字段**：例如 B4 把 30 个战斗中间量塞进每势力行、其中 28 个只在打仗时
   非中性——那时「中性值可省」才开始回本（而且因为 §7 的声明表已在，落地只要 encode/decode +
   一条无损 property test）。
3. **换列存那天**：parquet 里 null 免费、schema 驱动 —— 直接拿到，别手搓。

量化判据：**当「处于中性值的字段数 ÷ 全部字段数」在典型回合里超过约 30% 时**再考虑。
现在这个比例：扣掉 `capital` 之后约 2%。
