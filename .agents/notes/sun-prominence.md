## 0. 结论先写

**日珥 = 少数「大片曲面条带」的几何 + 片元里一个「世界空间各向异性噪声场」。**

- **顶点**只决定「在哪里、多大、往哪边倒」；
- **片元**在那个共享的世界空间场里，把每条带子**切成几十根并排的细长日珥**。

一切「在一个着色器里沿视线积分/解析求交」的做法都出不来须（§1）；
而「几千根细针」的做法**密度与细腻只能二选一**（§2 的第一版），所以被上面这个分工取代。

## 1. 三条弯路（都真的走完了，别再走）

| 做法 | 为什么不行 |
|---|---|
| ① 等半径**球壳** | 壳在几何上**没有径向厚度**：外缘永远等于轮廓线 ⇒ 只能读成「一圈均匀硬红环」 |
| ② 并入日冕的**体积积分** | 掠射时视线几乎与日面**平行**，穿过约 1.3 rad 的弧 ≈ **三十多根针的间距** ⇒ 积分把它们**平均成一层雾**。所以「加频率/改强度/换噪声」全都无效 —— 不是参数问题，是**积分这个动作**抹平了切向结构 |
| ③ 每像素**解析求交** | 形状出来了，但是 **2.5D**：没有真正的三维遮挡与视差；而且「用哪一点当切向坐标」很难选（用最近点方向时 `dot(u,t1) ≡ 0` ⇒ 噪声退化成常量 ⇒ 一条光滑亮边） |

## 2. 两个阶段（第二版取代了第一版，别退回第一版）

### 阶段 A（第一版，已被取代）：「几千根细针」

`PlaneGeometry(1,1,1,4)` + 每实例 `(aDir,aSide,aBend,aParam)`，
`p = aDir*(R−0.015) + aDir*(h·t) + aBend*(curve·h·t²) + aSide*(x·w·taper(t))`，
`PROM_MAX = 12000~30000`，宽度只有 `0.0035R`。做对的部分（**保留**）：

- 根部**埋进日面 0.015**（不然掠射时片与球的切点会露出一条缝）；
- 材质 `AdditiveBlending` + `depthWrite:false` + **`depthTest:true`** ⇒ 发光体互相叠加，
  但会被**行星**挡住（这是②无论怎么调都拿不到的东西）；
- `frustumCulled = false`（实例属性不在包围球里 ⇒ 不关会整批消失，「日珥时有时无」）；
- **掠射衰减**`graze = 1 − |dot(viewDir, normalize(vWorld))|` + 盘面衰减
  ⇒ 不这样的话**整个可见半球被盖住**（像一只毛球），而 304Å 的盘面该是斑驳的表面。
- 确定性 PRNG `mulberry32(0x5eed1234)`（**不要用 `Math.random`**，截图判据要可复现）。

**为什么被取代（用户原话：「更稀疏但大片的曲面条带…带子内部用 shader 实现细腻的日珥纹理」）**：

1. **实例数就是密度的上限**：要"密"就得几万根，而每根还是**光板一块**（片元里只有横向剖面
   + 一个断裂噪声），于是"密"与"细腻"只能二选一。
2. 每根的朝向是**各自 random** 的 ⇒ 一片**等距、等倾角的刷子**，形态上完全没有结构
   （用户：「带子的群面形态太均匀，连朝向都是一样的」）。

### 阶段 B（现在）：**大片曲面条带 + 片元里的本地空间纹理**

分工写在 `sun.js::buildPromCards` / `prom.vert` / `prom.frag`：

| 谁 | 负责 |
|---|---|
| `sun.js` | 根部方向（球面均匀）、高度、宽度、拱度、弯曲量、种子。`PROM_MAX = 5000` |
| `prom.vert` | 顺**世界空间场**倾倒 + 顺场**扭**（§3）、横向偏移换算成角度（**曲面**而不是平板）、上缘/侧缘起伏 |
| `prom.frag` | 在**本地空间**把带子切成十几~几十根细长日珥（§4），再加亮节/每丝长度/尖端 |

- **尺寸**：高度 `0.045R~0.28R`（拱 `0.09R~0.30R`），宽度（弧长）`0.075R~0.34R`
  —— 比细针版宽**一两个数量级**（"稀疏但大片"）。
- **曲面**：`p = normalize(up + side·(x·w/rad) + (bend·curve + sweep·twist)·h·t²/rad) · rad`。
  横向偏移**换算成角度**（`rad` 处的弧长 `s` ↔ `s/rad` 弧度）⇒ 整片带子贴着球面弯。
  这就是"曲面片"里的那个**曲面**；平板会被一眼看出来。
- **拱（loop）**：`rise = t(1−arc·t)` 归一化到峰值 1（`arc=1` 时尖端落回日面高度）。
  ⚠ 用 `t(1−arc·t)` 而不是 `sin(π·t)`：sin 让**根部斜率不为 0**，拱脚会斜插进日面
  （像被风吹歪的草），而真实日珥环的脚是**垂直扎进**色球的。
  ⚠ `rise` 必须归一化：不归一化时 arc 一大峰值就从 1 掉到 0.25，须会莫名缩水。

## 3. `px/sun/flow.glsl`：共享的是**带子的扭曲**，不是带子内部的纹理

> ⚠ **这一节第一版我写错了，改过一次，别再混**（用户原话：
> 「你弄错了一件事情，我说的共享噪声空间是**带子的扭曲**，带子内部的纹理是**本地空间**」）。

两个函数，形状（`prom.vert`）与纹理（`prom.frag`）共用一个世界空间场：

```glsl
vec3 promFlow(vec3 p, float t);          // 平缓的三维矢量场
float promMask(vec3 p, float t);         // 平缓的标量场：哪里有日珥（成片，不是均匀铺满）
vec3 promTangential(vec3 n, vec3 F, vec3 fallback);   // 把场投到切平面 ⇒ "朝哪边倒"
```

**它管什么**：带子的**朝向**与**沿长度的扭曲**。
相邻根部的场几乎相同 ⇒ 带子**成片地倒向同一侧、扭向同一侧**，而场本身在球面上缓慢转
⇒ 不同区域不一样。**这不是"加了随机"，是"去掉了均匀"**（用户要的正是这个）。

**它不管什么**：带子**内部**那些细小的日珥（§4）。那片纹理是**每条带子自己的本地空间**。

⚠ **频率必须平缓**：`promFlow` 用 `k = 0.42`（特征尺度 ≈ 2.4 世界单位 ≈ 0.37R），
`promMask` 用 `0.30`。频率一高，"相关"就退化成"各随各的噪声"，和 random 没区别。

### 曲线要**一条、平滑、一致**（用户："毛躁，末端好像有额外弯曲"）

带子的中轴**只允许有一条平滑的弯**：

```glsl
vec3 sweep   = promTangential(up, Ft, bend);           // 弯的**方向**来自共享场
vec3 bendDir = normalize(sweep + bend * aParam.z);     // aParam.z 只是 ±0.45 的**方向抖动**
float bendMag = uTwist * (0.45 + 0.75 * aKind.y);      // 强度只取**正**值，每片抖
... + bendDir * (bendMag * hh * t * t / rad)
```

三处"毛躁 / 末端多拐一下"的来源（都砍掉了，别再请回来）：

| 元凶 | 症状 | 处理 |
|---|---|---|
| 侧向摆动 `sw = sin(tπ)·sin(2πt + seed·2π)` | 沿长度的一个正弦 ⇒ **末段还在摆**，看起来"末端多弯了一下" | **删掉**（要个体差异靠强度和方向抖动，不靠加一条波） |
| 每片**带符号随机**的弯曲量 `curve ∈ [−0.7, 0.7]` | 相邻带子朝**相反**方向弯 ⇒ 整片日缘毛躁、不"一致" | 方向改由共享场给，每片只抖强度和 ±0.45 的方向 |
| 上缘/侧缘的顶点起伏给到 ±50% 高度 | 轮廓被锯开 | 收到 **±19%（高）/ ±12%（宽）** —— 只要"边界不是一条数学直线" |
| 每根丝末端淡出区间只有 0.38t | 几十根并排硬收 ⇒ 一片**毛刺** | 放宽到 **0.54t**，读成"散开" |

> 判断标准：把单独一条带子放大看，它的**中轴应该是一段光滑曲线**（一段抛物线），
> 不该有第二个拐点。

### 扭曲怎么写才对（踩过的坑）

```glsl
vec3 k0 = promTangential(aDir, F0, aSide);          // 根处的场 ⇒ 生长方向
vec3 up = normalize(aDir + k0 * tilt);
vec3 sweep = promTangential(up, Ft, bend);          // 上方 0.30R 处的场 ⇒ 往哪边歪
... + (bend*curve + sweep*twist) * (hh * t*t / rad) // 中轴沿长度平滑侧移
```

⚠ **不要用"横截面随 t 转"来表达扭转**（每一步把 `side` 对当前的 `up` 重正交化）。
那是数学上更"真"的扭转，但只有 8~12 段顶点 ⇒ 方向一摆就成了**折线**，
实测画面是一堆带尖角的折板（很难看）。要的是"整条带子缓缓歪过去"，
**用中轴的平滑侧移**（`t²`）表达就够了，而且它同样来自共享场 ⇒ 相邻带子歪向同一侧。

## 4. 一个带子内部怎么画出**很多细小的日珥**（**本地空间**）

用户原话：「一个带子内部应带描绘很多细小的日珥」「带子内部的纹理是本地空间」。
做法：**参数化在本地**（`vUv`：x 沿带宽、t 沿带长；外加每片的 `vSeed`），
但用 `vSize`（这条带子的**世界**宽/高）把 uv 换算成世界尺度再乘频率 ——
这样丝的粗细对**任何尺寸**的带子都一致，而纹理**跟着带子走**（带子扭过去，纹理跟着扭）。

```glsl
float u = x * vSize.x;   float v = t * vSize.y;              // 世界单位（本地系）
vec3 lp = vec3(u * uFilFreq, v * uFilFreq * uFilAlong, vSeed * 9.0);
float c1 = ridgedP(lp);                                      // 主丝
float c2 = ridgedP(lp * 2.3 + vec3(11.0, 3.0, 7.0));         // 丝上的更细结构
float thread = smoothstep(0.22, 0.58, c1) * (0.55 + 0.60 * smoothstep(0.24, 0.62, c2));
```

- `uFilFreq = 26`（1/世界单位）⇒ 丝的间距 ≈ 0.038 世界单位 ≈ `0.006R`；
  `uFilAlong = 0.14` ⇒ 顺带长方向频率只有 1/7 ⇒ 丝是**长**的。
  ⇒ 一条宽 `0.075R~0.34R` 的带子里**并排着十几到二十几根丝**。
- ⚠ **绝不能把内部纹理钉在世界坐标上**（第一版就是这么干的）：纹理尺度被"世界单位"锁死，
  一条窄带子里只剩两三根丝，而且带子扭过去纹理不动（纹理和形状脱钩）。
- **每根丝有自己的长度**：横向一个与丝的间距同量级的低频场给每根丝一个"到多高就散"的高度
  `tEnd = 0.40 + 0.52·vnoise(vec3(u·uFilFreq·0.85, vSeed·17, t·0.03))`，
  `threadLen = 1 − smoothstep(tEnd−0.26, tEnd+0.12, t)`。
  ⇒ 一片带子读起来是**几十根长短不一的日珥**，而不是一块均匀的条纹布。
  ⚠ **上限必须 < 1**：`tEnd > 1` 的那些丝会一直顶到几何上边缘 ⇒ 又出现一条**笔直的截断**。
  压到 0.92 之后每根丝都在几何边界**之前**淡掉。
- ⚠ **根部不能取实心 1.0，也不能取 0**：
  - 取 1.0 ⇒ 露出**四边形的几何边**（插片最大的破绽）；
  - 取 0 ⇒ 带子读成**一缕缕烧完的灰**；《群星》里的日珥是**发光的等离子体**。
  现在根部 `0.82`，往上 `0.30 + 0.95·thread` —— 带子整体是一团发光体，丝是它上面更亮的筋。


### 边不能是直的（必须在**几何**上做）

一块矩形板最大的破绽是它的四条直边。**只在片元里做 alpha 衰减是"淡出"，剪影仍然是直的**。
所以起伏放在**顶点着色器**里（沿**宽度**方向采世界空间噪声去调制高度与宽度）：

```glsl
vec3 wq = normalize(aDir + side*(x*w/uSunR)) * (uSunR*1.9);
float e1 = fbmP(wq + vec3(0,0,uTime*0.020));
float e2 = fbmP(wq + vec3(17,5,uTime*0.020));
float hh = h * (0.48 + 0.98*e1);   float ww = w * (0.62 + 0.62*e2);
```

⇒ `PlaneGeometry(1,1,5,8)`（**横向 5 段**，1 段的话顶边只由两个顶点决定，还是折角）。
同一族噪声 ⇒ 起伏在带子之间也是连续的。

> **踩过的坑（值得记）**：上一版的"硬矩形上缘"我一度以为是尖端淡出（`tip`）没生效，
> 把 `tip` 从 `smoothstep(0.55,1.0)` 改成 `smoothstep(0.10,0.35)` 重拍 —— **画面完全没变**，
> 于是排除掉 shader 里的长度淡出，确认是**几何剪影**。
> ⚠ 当时第一次调试用**加色**混合输出 `(tip,lateral,fil)`，几十片叠加直接饱和成白色，
> 什么也读不出来；**把材质临时改成 `NormalBlending` + `depthWrite:true`** 才看清一片片的
> uv/参数分布。这条路以后别再走一遍。

## 5. 光球（`photo.frag`）：配色**反解**，亮度按**分位数**分层

隔着 `ACES + exposure + sRGB` 三跳，照着屏幕调 HDR 会一直调歪（ACES 在 0.7 以上压得极扁、
红通道先饱和 ⇒ 「再亮一点」的结果是**丢掉颜色和结构**）。所以：

```
node scripts/shots/run.mjs --solve 192,62,8   →  HDR [0.5627, 0.0756, 0.0026]
```

六个锚点（`C_VOID/C_HOLE/C_MID/C_ACT/C_CORE/C_WHITE`）取自两张参考图上量到的分位数
（`node scripts/shots/refstat.mjs <图>`）。
⚠ `C_WHITE` 是**加色**用的、**不进 ramp**：参考图 p99 比 ramp 的顶还亮一截，
而 ramp 是全局映射，抬顶会把整片日面都拉白。

**这一轮真正解决"不够亮"的地方不是整体乘一个数，而是把两端的极差拉开**：
旧版 p10..p90 只有 21..146（"均匀的脏橙"），参考图是 51..190。所以
`heat = 0.38 + (mott−0.5)·0.72 − 0.38·hole + 0.32·act + 0.18·core`，
另加 `col += C_WHITE*(0.50·burst²) + C_WHITE*(0.09·core²) + (0.90,0.20,0.008)*(0.16·core)`
（后两项是**热核的光晕**：ramp 只能改颜色、不能"往外发光"）。

临边 `limb = (1 − 0.36·mu^1.7) / 0.816`：304Å 是**临边增亮**，SDO 参考图实测
盘心 68 → 0.85R 125 → 日缘 147。⚠ 除以 `0.816`（盘面上的面积加权平均，`E[mu]=2/3`）
而不是 1.0，这样"盘面平均电平"仍等于锚点电平，ACES 的饱和度才不会跑。
最外一圈另加 `col += C_RIM * (0.55·(1−mu)^5)`（色球亮边，HDR 峰值 > 1.5 ⇒ 喂 bloom）。

## 6. 纹理：格点噪声的**方格纸**（顺手修掉的全局问题）

现象：日面放大是一片**小方块**（每块约 8 px = `p*SC` 里 SC 的格距）。
根因：`vnoise` 是**三线性插值的格点噪声**，等值线自带轴向方格；`fbm/ridged` 叠八度时
所有格子**朝向相同** ⇒ 叠出来是一张方格纸；`ridged` 的 `n*n` 又把等值线锐化，所以它最明显。

修法（两层）：
1. **八度之间换格子朝向**：`px/noise/rot.glsl` 里那个正交矩阵（绕 (0.30,0.70,0.6481) 转 47°），
   `fbm`/`ridged` 每进一个八度乘一次。单独一个文件是为了 `photo.frag` 同时 include
   `fbm` 与 `ridged` 时不重复定义常量。
2. **换成梯度噪声**：`px/noise/perlin.glsl` 的 `pnoise/fbmP/ridgedP`（12 个固定方向的 Perlin，
   每角点仍只 1 次 hash ⇒ 与 vnoise 同阶）。**太阳用的是梯度噪声**；行星/云/星云仍在用 value 版
   —— 换过去会改它们的外观，属于**另一个需要单独验收的任务**（`earth` 场景已就绪）。
3. 光球的八度**封顶 4**：uFbmOct=7 时最细一层是 `SC*2.13⁶` ⇒ 屏幕 0.1 px，纯属亚像素闪烁。
4. 米粒组织**自己也被一个中频位移场拖动**（`pg = p*SC + (fw−0.5)*1.7`，`fw` 的频率是 `SC*0.10`）：
   ⇒ 亮暗纹从"斑点"变成**卷曲的丝**。⚠ 位移频率只比米粒低一档：太高＝把米粒打散成噪声，
   太低（用低频的 `pw`）＝在一个米粒尺度上近似常数，等于整体平移，纹路还是直的。

## 10. 几何密度与 **LOD**

### 10.1 先回答"three.js 支不支持曲面细分"：硬件的不支持

| 层 | tessellation |
|---|---|
| WebGL2（现在跑的就是它） | **没有**。= OpenGL ES 3.0，GLSL ES 3.00 里没有 tessellation control/evaluation 这两个 stage（那是桌面 GL 4.x；ES 侧的 `EXT_tessellation_shader` 浏览器不暴露） |
| WebGPU / WGSL | **也没有**。core spec 只有 vertex / fragment / compute |
| three 给的替代品 | 全是 **CPU 侧的一次性预剖分**：`TessellateModifier`（r169 在）、`ParametricGeometry`（r169 在）、`SubdivisionModifier`（**已删**，CDN 404）；`displacementMap` 也要先有密网格 |

**但这件事对我们不成立**：带子的曲面是**解析**的 —— 顶点着色器里就在算 `p(u,v)`。
所以"细分级别"= **一片喂多少顶点**，与硬件特性无关，按档位给就行（想要"自适应"，
WebGL2 里也只有 CPU 预剖分这一条路）。

### 10.2 参数化必须**均匀**（被纠正过，别再"优化"回去）

一度想按位置挪顶点密度（直须密在根部、拱密在拱顶）。**这是错的**：
带子的弯曲/扭曲完全由 `promFlow` 那个**噪声场**决定 ⇒ **曲率在哪不固定**，
"固定密集的地方"正好会落在直线段上，而真正拐弯处依然只有两三段 ⇒ 折角照旧，
还白白浪费一半顶点。真正跟得住曲率的只有"按弧长重参数化"（要在顶点着色器里做积分，不值得）。
⇒ 正确做法：**均匀给足 + LOD**。

### 10.3 LOD 的两个维度（都实现了）

| 维度 | 在哪 | 降的是什么 |
|---|---|---|
| **画质档** | `TUNING.TIERS[].promLod` → `PROM_LOD = [[9,24],[7,16],[5,10]]`（`[横段, 长段]`） | 几何**平滑度** |
| **距离** | `sun.js::update` 里按**日面在屏幕上的半径**选档（`<45px ⇒ lod2`、`<130px ⇒ lod1`） | 同上 —— 远景（`sun-wide`）日面才几十像素，顶档纯属浪费 |
| （已有）**数量** | `TUNING.TIERS[].prom` → `instanceCount` | **密度** |

- 三个 LOD **共享同一份实例属性**（同一个 `BufferAttribute` 挂到多个 `InstancedBufferGeometry` 上），
  切档只换 `prom.geometry`，**不触发着色器重编译**、不重建数据。
- ⚠ 距离要用**太阳到相机**的距离：`g.getWorldPosition()` 再 `distanceTo`。
  写 `camera.position.length()` 只是"太阳恰好在世界原点"时的巧合，天体一动就悄悄错。
- **纹理不受 LOD 影响**：带子内部那些细丝全在片元里（§4），两个维度都不动它。

### 10.4 实测（RTX，1280×800，**特写视角** = `sun-disk` 的相机）

`node scratch/perf.mjs <url> <档> <次数> --view 0,4.86,19.5`
—— ⚠ **必须给 `--view`**：不给的话用的是页面自己的 `fitCamera`（**远景**），
那个视角下日面只有几十像素 ⇒ 距离 LOD 直接降到 2，量到的是"便宜的那一档"
（6 ms），拿它当特写开销会得到一个**好得离谱**的数。

**日珥层值多少钱**（ultra，5000 片，同一视角、跑完等机器稳定）：

| 配置 | frameMs |
|---|---|
| 日珥关掉（`?tune=coronaOn:0`） | 17.2 |
| 1250 片 | 20.2 |
| 2500 片 | 22.3 |
| **5000 片** | **27.3** |
| 5000 片 + 少一次 `ridgedP` | 24.5 |
| 5000 片 + 八度 3→2 | 22.4 |

⇒ ① 开销基本随**实例数**线性（不是饱和的片元瓶颈）⇒ 密度是最直接的旋钮；
② **八度是最贵的单个旋钮**（3→2 省 ~4 ms），其次是减少一次 `ridgedP`（~2.5 ms）。

**分档后的阶梯**（特写视角）：

| 档 | prom | lod | 八度 | frameMs |
|---|---|---|---|---|
| ultra | 5000 | 0 | 3 | 23.9 |
| high | 3000 | 1 | 3 | 12.8 |
| medium | 1800 | 1 | 2 | 7.0 |
| low | 800 | 2 | 1 | 6.2 |

⚠ **顺手修掉一个"假分档"**：日珥材质的 `uFbmOct` 原本是 `min(3, oct)`，
而所有档的 `oct` 都 ≥3 ⇒ **恒等于 3**，medium/low 白花钱。现在 `oct-2` 再夹住
（ultra 3 / high 3 / medium 2 / low 1）。

**远景**（`sun-wide`，日面几十像素，距离 LOD 自动降到 2）：**6.1 ms**。
真实游玩视角就是这一类，所以"特写 24 ms"是**故意贴近看**时的代价；
另外默认打开的**自适应分辨率**（`tier.adaptive`）是片元开销的第二道保险
（本文所有测量都带 `tune=adaptive:0`，即**关掉**它量的，是悲观值）。

⚠ 单次读 `debug().frameMs` 噪声极大（同一配置我读到过 17.9 / 27.3 / 40.7），
**必须多次取中位**，而且要在机器稳定后测（连续测四轮时数值会单调漂移）。

### 10.5 可观测性（不然后面没法断言"远景真的降了"）

- `debug()` 多了 `promLod`（当前生效的 LOD 等级）。
- `run.mjs` 把它打进 `.json` 的 `ready` 里并在终端行首显示：`tier=ultra promLod=0`。
  ⚠ **`ready` 是 `setView` 之前读的** ⇒ 那里的 `promLod` 是"fitCamera 远景"那一下的数，
  拿来判断本景最终用哪档会**正好反着**（贴近的 limb 景会被记成 lod=2）。
  现在取景并稳定之后再读一次（`settled`），两个值分开存。
  这一条是**加可观测性时才发现的**：加之前 `sun-limb` 报 lod=2、`sun-wide` 报 lod=2，
  看起来像"贴近日面反而降级"。

**核显没量过**（见 §11）。
